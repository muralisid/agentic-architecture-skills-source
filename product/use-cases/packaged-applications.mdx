<PlainTerms>
Most large organisations run their core work on packaged software, also called COTS (commercial off-the-shelf). Billing, finance, asset and field systems are bought, not written. The vendor owns the code. So the question is not only "should we build an agent?" It is also "will the vendor ship one for our version, and when?" The one thing to remember: wait for a vendor only when a dated agent exists for your edition. Build thin where the work crosses several packages.
</PlainTerms>

## Why packaged software changes the question

Two pieces of advice are common. One says wait for the vendor to put agents inside the package. The other says build agents on the glue around the packages: middleware, portals and reporting. Neither works as a blanket rule.

This guide's position:

- **Inside one package**, on a supported edition, with a dated agent that is generally available: wait or buy.
- **Across packages**, or on an edition the vendor excludes: build, and build thin.

Generally available (GA) means any customer can buy it and run it in production, not a preview. Vendors are moving into every glue layer at once. So the opening is the join across packages, not each layer.

## Where vendor agents really are

**In short:** Every large package vendor now sells agents. Most are tied to cloud editions. Dates move, prices are open, and no vendor publishes how many of its agents run in production.

**Dates move.** ASUG is the SAP user group. SAP's utilities billing-exception agent was "scheduled for Q2 2026" in one ASUG article (21 January 2026) [vendor]. A Billing Document Agent was "planned for Q3 2026" in another ASUG article (27 May 2026) [vendor]. The two scopes may differ. So this is a likely slip, not a confirmed one. **Counts do not compare.** Vendors count agents, assistants, skills and apps differently. None publishes how many of its agents run in production. Forrester calls this the main gap in Oracle's case.

**The layer that governs agents across vendors is contested, not empty.** SAP, ServiceNow, Workday, Microsoft and MuleSoft each offer to register other vendors' agents (diginomica, 5 May 2026; CIO.com, 12 May 2026) [vendor]. Each wants to be the one list of every agent. Workday's claim that its own registry is generally available is unconfirmed ([what has shipped](/architecture/agent-lifecycle#what-has-shipped-and-what-has-not)).

## The six tests

**In short:** Run six tests on each process, in order. Tests three and four are the new ones for packaged applications.

1. **Does it need an agent?** A predictable task needs ordinary code. Questions over a fixed set of documents need plain retrieval. This follows Microsoft's Cloud Adoption Framework (updated 2 June 2026) [vendor].
2. **Can it be evaluated?** Domain experts must be able to write pass-or-fail tasks from real failures. This is the existing gate in [the use-case portfolio](/library/frameworks/use-case-portfolio). A valuable process that fails it goes to the make-it-evaluable queue. It is neither built nor rejected.
3. **Is the process inside one package or across several?** Inside one package, the vendor holds the data and the permissions. It is likely to ship an agent. Across several packages, no vendor agent covers the whole job.
4. **Is a vendor agent GA on this edition, or dated within two quarters?** Count only agents marked GA in release notes. Treat "announced" as unavailable. Check the price after any free period ends.
5. **What is the consequence class?** Score the agent with the [risk profile](/architecture/risk-profile). Check which [deterministic zones](/architecture/deterministic-zones) it touches. A bill change is a money action, whoever built the agent.
6. **Score impact, feasibility and desirability.** Microsoft's framework scores each from 1 to 5. Then check that your reviewers can absorb the load across the whole portfolio.

Tests three and four appear in no published framework found in this guide's research. The only fully documented selection method found is Microsoft's. It asks whether a software-as-a-service (SaaS) agent already meets the need. It does not ask which edition you run, or when an agent will arrive.

### Five outcomes

| Outcome | When it applies | What you do |
|---|---|---|
| Wait or buy | Inside one package, on a supported edition, with an agent that is GA or dated within two quarters | Use the vendor's agent. Register it. Re-check the date each quarter. |
| Build thin across packages | The process crosses packages, the edition is excluded, or nothing is dated within two quarters | Build a small agent that works through governed <Term k="api">APIs</Term>. Leave each package's rules inside the package. |
| Wrap | You use vendor agents in several packages | Use them. Own the interface inventory, the semantic layer, the registry and the policy. |
| Not an agent | Test one fails | Use ordinary code, a fixed workflow or plain retrieval. |
| Prepare first | Test two fails, or the data or interfaces are not ready | Fund the definition of success, the data and the interfaces before any agent. |

Thin means small and easy to retire. The agent keeps no business rules of its own. When a vendor agent later covers the job, you switch yours off. The interfaces and definitions stay. Describe each agent, bought or built, with the [four questions](/use-cases/agent-roles).

## Where enterprise-built agents land in a utility estate

**In short:** Vendors cover most single systems. The strongest place to build is the join across billing, outage, mapping and field systems. No measured outcome exists yet for any enterprise-built portal, middleware or reporting agent.

| Portals | SAP for Me with Joule [vendor]. Kraken agents live at one unnamed utility on about 1.3 million accounts, June 2026 [vendor]. | Vendor agent for journeys inside one system. Build for journeys across billing, outage and field. | No measured outcome for an enterprise-built portal agent. |
| BI (business intelligence and reporting) | Agentic features now baseline in Gartner's June 2026 analytics review, per a consultancy summary. Databricks Genie GA 12 June 2025 [vendor]. | Use the vendor's agent. Invest in the <Term k="semantic layer">semantic layer</Term>, read-only database roles and the user's own identity. | No independent adoption data. |
| The join across systems | No vendor covers outage messaging and work orders across billing, outage, GIS and field. | The strongest build candidate. | Architectural case only. |

Take an outage. The billing system knows who is affected. The outage system knows what failed. GIS knows where. The field system knows who is on the way. A customer message and a work order need all four. No single vendor's agent sees all four today. Gartner expects agent networks that span applications only in 2028 (as reported 27 August 2025).

The evidence is weakest where the case for building on the glue leans hardest. The case for portals, middleware and BI is architectural, not measured. For the work itself, see [Utilities](/use-cases/utilities) and [Energy](/use-cases/energy).

## What to own whatever you buy

**In short:** Four things stay yours whichever agents you run. They also make each vendor agent easier to replace.

- **Interface inventory.** List every interface between systems, with its owner and purpose. Retire dead flows. Decide which ones become agent tools. SAP's own guidance keeps existing roles in force and starts read-only [vendor].
- **Semantic layer.** Keep one set of business definitions under every reporting agent. Databricks says Genie's answer quality depends on curation [vendor].
- **Agent registry.** Keep one <Term k="registry">registry</Term> that lists every agent, including the ones inside vendor products. Cover <Term k="two estates">both estates</Term>: agents behind your own gateway, and agents that run on a vendor's controls. Vendors offer to hold this list. Whichever you use, it must hold other vendors' agents too. The record fields are on [the agent lifecycle page](/architecture/agent-lifecycle#the-registry-record).
- **Policy at the gateway.** Put access and approval rules at your own <Term k="gateway">gateway</Term> and <Term k="policy decision point">policy decision point</Term>. Do not leave them inside each vendor's agent. Then a change of vendor does not change the rules.

## Counterpoints, both ways

**In short:** The evidence does not settle wait versus build. It shows where each argument is weakest.

**Against building on the glue layer.**

- **Poor data.** SAP's chief executive said no AI agent can make up for poor data (ERP Today, Sapphire 2026 keynote, May 2026) [vendor].
- **Fragile legacy interfaces.** Old systems lack real-time execution, modern APIs and secure identity (Deloitte Tech Trends 2026, 10 December 2025).
- **Vendor encroachment.** Vendors are building into integration, reporting and portals at once (SAPinsider, 13 August 2026; Futurum, 12 June 2026). A thick custom layer may be overtaken.
- **Partner-built pilots do better.** In Deloitte's report, pilots built with partners reach full deployment twice as often as in-house ones. It is the only quantified build-versus-buy result found. Its method is not visible.

**Against waiting.**

- **Excluded editions.** Oracle's agents need its cloud applications. SAP ties its AI to cloud editions or a committed migration. On those vendors, waiting means waiting to migrate.
- **Open prices.** Joule Studio is free only through 2026. Oracle's renewal pricing is unresolved. Salesforce changed its pricing model within months.
- **Slipping dates.** The SAP utilities agent above moved by a quarter between two articles. One SAP customer at Sapphire 2026 would build a financial-close assistant itself if SAP's was three months away (CIO.com, 12 May 2026).
- **Lock-in.** Putting agents inside one platform may deepen dependence on that vendor (Futurum, 12 June 2026).

The two sides are not equal on evidence. The case against the glue rests on documented data and interface problems. The case against waiting rests on dated facts about editions and prices. Lock-in is analyst opinion.

## Evidence and limits

- Vendor counts, dates and prices are vendor-published and marked [vendor]. This page is re-verified each quarter.
- With no production counts, the only fair comparison is GA against announced, from the release notes.
- Gartner's build-versus-buy notes (July and August 2026) were seen only as abstracts. Gartner's analytics review was read only through a consultancy summary. Gartner's own pages refused access.
- Several vendor pages returned errors, including Salesforce's page for energy and utilities. No source was found for Oracle's utilities agents.
- The shipped status of SAP's Q2 and Q3 2026 utilities agents is unconfirmed. Sources conflict on whether SAP's MCP Gateway is GA in a given tenant. No per-agent GA list from Sapphire 2026 was found.
- No named custom agent was found that a vendor feature later replaced. No named customer was found who was let down by a vendor agent.
- The six tests, the two-quarter window and the five outcomes are this guide's position. They have not been tested against outcomes.
