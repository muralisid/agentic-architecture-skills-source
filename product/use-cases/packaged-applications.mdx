Most of the processes an enterprise wants to automate run inside packaged software it cannot rewrite. Billing, finance, asset and field systems are bought, not written. So the question is not only whether to build an agent. It is also whether the vendor will ship one for your edition, and when. Two tests answer it. Is the process inside one package or across several? Is a vendor agent generally available on your edition, or dated within two quarters? Inside one package, with a vendor agent available or dated, wait or buy. Across packages, or on an excluded edition, build a thin agent of your own.

## The two tests

Two questions come first. Does the work need an agent at all, or will ordinary code do? Can its result be judged? [Choose where to start](/use-cases/choose-where-to-start) covers both.

1. **Is the process inside one package or across several?** Inside one package, the vendor holds the data and the permissions, and is likely to ship an agent. Across several packages, no vendor agent covers the whole job.
2. **Is a vendor agent generally available on your edition, or dated within two quarters?** Generally available means any customer can buy it and run it in production. Count only agents marked that way in release notes. Treat an announced agent as unavailable. Check the price after any free period ends.

## Wait, buy or build thin

| Outcome | When it applies | What you do |
|---|---|---|
| Wait or buy | One package, a supported edition, an agent available or dated within two quarters | Use the vendor's agent. Register it. Check the date each quarter. |
| Build thin | Across packages, an excluded edition, or nothing dated | Build a small agent that works through governed <Term k="api">APIs</Term>. Leave each package's rules inside it. |
| Use and govern | You use vendor agents in several packages | Use them. Own the interface inventory, the business definitions, the registry and the policy. |
| Not an agent | The work does not need an agent | Use ordinary code, a fixed workflow or plain search. |
| Prepare first | The result cannot be judged, or the data or interfaces are not ready | Fund the definition of success, the data and the interfaces first. |

Thin means small and easy to retire. The agent keeps no business rules of its own. When a vendor agent later covers the job, you switch yours off. The interfaces and definitions stay.

Then treat every agent the same, bought or built. Answer [the four questions](/architecture/agent-types) for it. Score its <Term k="impact">impact</Term>, meaning what it can damage, on [the risk profile](/architecture/risk-profile). Check which [deterministic zones](/architecture/deterministic-zones) it touches. A bill change is a money action, whoever built the agent. Then score it for [the use-case portfolio](/library/frameworks/use-case-portfolio).

## Where vendor agents are today

As of 14 October 2026, every large package vendor sells agents. Most need the vendor's cloud edition. Oracle's agents are not coming to E-Business Suite, JD Edwards, PeopleSoft or Hyperion. Prices are still moving. Dates slip. An SAP billing agent for utilities moved from Q2 to Q3 2026 between two articles [vendor]. No vendor publishes how many of its agents run in production.

No measured result exists yet for an agent inside either billing system, or for a portal agent an enterprise built. The one measured result on the [line of business and OT](/layers/r05-lob-and-ot) page is for the asset-data work. No utility found lets an AI agent operate protection or switching.

Take an outage. Billing knows who is affected, the outage system what failed, GIS where, and the field system who is coming. A customer message and a work order need all four. No single vendor's agent sees all four today. That join is the strongest place to build. Gartner expects agent networks across applications only in 2028 (as reported 27 August 2025).

## What to own whatever you buy

Four things stay yours whichever agents you run. They also make each vendor agent easier to replace.

- **Interface inventory.** List every interface between systems, with its owner and purpose. Retire dead flows. Decide which ones become agent tools.
- **Business definitions.** Keep one set of business definitions under every reporting agent, often called a <Term k="semantic layer">semantic layer</Term>.
- **Agent registry.** Keep one <Term k="registry">registry</Term> of <Term k="vendor-embedded agent">your own agents and vendor-embedded agents</Term>. Agents you build run through your gateway. Vendor-embedded agents run on the vendor's platform, and you govern them through its settings. Several vendors offer to hold this list [vendor]. It must hold other vendors' agents too. [The agent lifecycle](/architecture/agent-lifecycle) lists the record's fields.
- **Policy at the gateway.** Put access and approval rules at your own <Term k="gateway">tool gateway</Term> and <Term k="policy decision point">policy decision point</Term>, not inside each vendor's agent. Then a change of vendor does not change the rules.

## Evidence and limits

The evidence does not settle wait versus build. The case against building on middleware, portals and reporting rests on documented problems. Poor data limits any agent, as SAP's chief executive said in May 2026 [vendor]. Old systems lack modern APIs and secure identity (Deloitte, 10 December 2025). Vendors are building into the same places (SAPinsider, 13 August 2026). The case against waiting rests on dated facts about editions, prices and slipping dates. Lock-in is analyst opinion (Futurum, 12 June 2026).

The sources stop short in several places. No named custom agent was found that a vendor feature later replaced. No measured outcome exists for a portal, middleware or reporting agent an enterprise built. No published framework found asks either test. Microsoft's Cloud Adoption Framework comes closest (updated 2 June 2026) [vendor]. The two tests and the two-quarter window are a proposal, not yet tested against results.
