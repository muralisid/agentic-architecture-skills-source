An agent changed a record in a business system. Who asked for it, and under whose permissions did it act? The delegation chain answers both questions for every action. The agent has its own registered identity. At the gateway it takes on the permissions of the person who asked, and no more. The business system records the action against that person. At every later hop, access can only get narrower. So an agent can never do anything its requesting user could not do.

## Three levels of agent identity

Three levels describe how an agent is identified.

- **Shared credentials (ID1).** The agent uses a person's login or a shared service account. Nobody can tell the agent's actions from the person's. Avoid it.
- **The agent's own identity (ID2).** The agent has its own registered account, called an <Term k="agent identity">agent identity</Term>. It holds only the access its task needs and uses short-lived credentials. It has a named sponsor and a [risk tier](/architecture/risk-profile). This is the minimum for any agent in production.
- **The agent's own identity plus an agent user account (ID3).** Some agents also need a mailbox, a calendar seat, or a seat in a meeting or chat. That needs a second account, an <Term k="agent user account">agent user account</Term>. It is a separate decision, made for a few long-lived agents.

Microsoft's products draw the same line. An agent identity lets an agent act on systems. An agent user account lets it join a meeting or a chat.

## Hop 1: the agent's own identity

Every agent is registered before it gets any credential. Its identity is an account in its own right. It holds <Term k="least privilege">least privilege</Term>, meaning only the access its current task needs. Its credentials are short-lived. It carries a named <Term k="sponsor">sponsor</Term> and a risk tier. Agent identity belongs to identity and policy, one of [the seven capabilities](/architecture/system-view) an agent platform provides. It is built in the [security and identity layer (R10)](/layers/r10-security-and-identity).

The starting point is poor. Non-human identities outnumber human ones by roughly 100 to 1 [vendor]. About 97 percent of them hold more access than they need [vendor].

Three kinds of <Term k="workload identity">workload identity</Term> are in production. A workload identity is the machine version of an ID badge. The first kind lives in a company directory, such as Microsoft Entra Agent ID [vendor]. The second comes from open standards work at the Internet Engineering Task Force (IETF). SPIFFE, one of those standards, already runs for agents at scale. The third extends OAuth, the standard web protocol for delegated access. Cross App Access is the main example [vendor].

## Hop 2: delegation at the gateway

The <Term k="gateway">tool gateway</Term> sits between agents and the systems they touch. It does not copy the caller's identity. It exchanges it, so the next system sees who asked and through which agent. The standard way is <Term k="token exchange">token exchange</Term> under OAuth (RFC 8693), or an on-behalf-of flow.

The gateway adds credentials at the moment of the call, so the agent never holds secrets. Access above a small baseline is granted <Term k="just-in-time access">just in time</Term> for one action. Then it drops back on its own. How the gateway checks each call is on [enforcement outside the model](/architecture/enforcement).

## Hop 3: run-as-user in the system of record

Inside the business system the agent acts <Term k="run-as-user">as the person who asked</Term>. It has that person's permissions and nothing more. The system keeps its own rules in force. Those rules say who may read, create, change or delete each record and field. Its audit log names the person.

The tool in between is a wrapper, not a second set of rules. Vendors now say this plainly. If the user cannot do something in the platform, their agent cannot do it either.

## Hop 4: narrower at every edge

A sub-agent gets a narrower scope than the agent that started it, never a wider one. The stated purpose travels with each hand-off.

In <Term k="ot">operational technology (OT)</Term>, the systems that run physical equipment, the agent is a security principal with least privilege. Assets without a registered name are not reachable on the network. Access can be cut in seconds.

## The sponsor and the agent user account

Every agent identity carries a named sponsor. The sponsor is the business person who answers for the agent's purpose and results. The sponsor is named when the agent is created, not added later. When a sponsor leaves, Microsoft passes sponsorship to the leaver's manager automatically (3 September 2026) [vendor].

An agent can be named and mentioned in chat without any user account. An agent user account is different. It brings a mailbox, a calendar seat, a licence, or a place in the HR system. It is optional, granted by an administrator, and revocable. Decide it by what the agent would do with it, and only for a few long-lived agents. Being nameable is not the same as having an account.

<GuideFigure id="support-accountability-enforcement" />

A sponsor answers for the agent. A rule is what stops an action. In one test, a phished employee's prompt asked an agent to send credentials out of the company. It worked in 24 of 25 attempts. The sponsor's name stopped nothing. You need both.

## Switch any agent off

You must be able to switch any agent off fast, from more than one place. <Term k="kill switch">Kill switches</Term> sit in the identity system, the <Term k="runtime">runtime</Term>, the gateway and the <Term k="harness">harness</Term>. The harness is the engineering shell around the model. Each switch covers what the others cannot. Time how long it takes to revoke one agent's credentials, in drills. Policy engines <Term k="fail closed">fail closed</Term>: if the engine fails, the answer is no.

The identity is created at the first stage of [the agent lifecycle](/architecture/agent-lifecycle) and revoked at the last. The level an agent works at is set on [the autonomy contract](/architecture/autonomy-contract). What its identity lets it reach is one of [the four questions](/architecture/agent-types) asked of every agent.

## A worked example: booking a referral in a hospital

This is a proposed design. A care coordinator asks an agent to book a referral appointment for a patient. The agent has its own identity and a named sponsor in the outpatient team. At the gateway, its request carries the coordinator's identity. In the scheduling system it acts as the coordinator. It can book only the clinics the coordinator can book. The audit log shows the coordinator, acting through the agent.

The agent passes one sub-task to a second agent that checks the referral letter. That sub-agent can read the letter and nothing else. To stop the agent, the hospital can revoke the identity, block it at the gateway, or stop its runtime. The full design is on [referral coordination](/use-cases/referral-coordination).

## Evidence and limits

This guide once called this the identity chain. The four hops rest on shipped products and on standards still in progress. As of October 2026, only Microsoft confirms on its own pages that its agent identity is generally available. Google confirms it for one runtime only. Other vendors' dates come from summaries or trade press.

The figures on non-human identities come from vendor surveys. A sponsored survey found that only 23 percent of organisations have a formal agent identity strategy (January 2026). The test of the phished prompt is a single account. The split between an agent identity and an agent user account follows Microsoft's products. Other vendors may draw the line elsewhere.
