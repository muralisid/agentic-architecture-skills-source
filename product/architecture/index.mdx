How do you turn model intelligence into useful enterprise work? Start with a task, such as checking a possible safety issue and arranging an inspection. A model and some documents can answer a question about it. Finishing the work needs more. The agent needs current information, permission to act, reliable business systems, and a person who answers for the result. This guide builds that in three parts: [the layers you own](/layers), [the lifecycle you run](/architecture/agent-lifecycle) and [the capabilities you add](/architecture/system-view). Controls are set as each agent passes through its lifecycle. For the whole route in order, read [Start here](/start).

## See the whole system first

<TeachingIllustration src="/images/architecture/enterprise-overview-v1.webp" expandable title="From a business goal to a confirmed result" alt="A business owner defines a goal. An agent uses intelligence and memory. It passes an independent permission check, then uses enterprise systems. The system returns a result for the agent to check. People oversee the work. Independent records show what happened." caption="Start with the outcome. Intelligence and memory help the agent work toward it. Tools, controls and people make that work possible." />

Take an agent that reviews vegetation near power lines. It needs images, the correct asset location and the inspection policy. It may ask for a closer look or propose an inspection. A separate permission check decides whether it can create the work order. The task ends with a confirmed result or a clear handover to a person.

This is a proposed design example. An image alone does not prove a safety risk. [The task walkthrough](/architecture/task-walkthrough) follows an inspection in more detail.

## The layers you own

Every agent works inside systems the company already runs. This guide groups them into fourteen layers. They run from infrastructure and compute (R01) to agent data engineering (R14). The layers hold the data, the records, the integration, the security and the people. Agents do not replace them. Agents add new demands on each one.

For intelligence, start with the [intelligence and learning layer (R06)](/layers/r06-intelligence-and-learning) and the [agent platform layer (R07)](/layers/r07-agent-platform). Both rest on [infrastructure and compute (R01)](/layers/r01-infrastructure). For memory, start with the [data platform layer (R02)](/layers/r02-data-platform) and the [agent data engineering layer (R14)](/layers/r14-agent-data-engineering). All of them depend on security, governance, monitoring and the people who run the service.

## The lifecycle you run

Every agent passes through nine stages: register, sponsor and owner, entitle, evaluate, approve, operate, change, periodic review and retire. Building and piloting come before stage 1. The <Term k="registry">registry</Term> record holds the agent's state: active, under review, deprecated or retired. AWS and Microsoft guidance both frame agent management as a lifecycle like this one.

The inspection agent is registered with a named <Term k="sponsor">sponsor</Term> before it touches a record. It is entitled to read imagery and draft work orders, and nothing more. It is evaluated on past inspections before anyone approves it. Once live, a change to its model sends it back to evaluate.

## The capabilities you add

Seven capabilities let agents run safely across the layers. Three let agents work: a runtime, a tool gateway, and [knowledge and memory](/memory). Four keep them in bounds: identity and policy, evaluation and release, observability and an audit trail, and human oversight. Each lifecycle stage calls on some of them.

Read the diagram around one task. A person sets the goal. The runtime runs the agent. Knowledge and memory supply the context. The tool gateway connects the agent to tools. Identity and policy limit what is allowed. Observability and audit trail record what happened. Evaluation and release test each change before it enters use.

Two rules hold the design together.

- **[Policy is enforced outside the model](/architecture/enforcement).** The model never checks its own permissions. The gateway and the policy decision point do.
- **The audit trail is written where the agent cannot touch it.** A separate channel records calls, approvals and outcomes.

## Connect intelligence and memory

Intelligence and memory need their own questions. How capable must the agent be for this task? What information must it have to make a supported decision?

<TeachingIllustration src="/images/architecture/intelligence-memory-loop-v1.webp" expandable title="How intelligence and memory work together" alt="Memory supplies the current task, past experience and reference evidence to intelligence. Intelligence chooses the next check. A separate permission gate comes before tool use. The result returns for checking. The agent then continues or finishes. Task progress is saved. Updates to shared memory need review." caption="Memory supplies context and evidence you can point to. Intelligence chooses the next step. The actual result decides whether to continue, stop or ask for help." />

In the inspection example, thread memory tracks the location under review and the checks already done. Longer-lived memory may supply an earlier inspection, an approved procedure or a past case. The agent uses that context to decide whether it needs another observation.

Keep two kinds of evidence apart. **Reference evidence** supports the decision: which image, record or procedure was used, and when it applied. **Execution evidence** shows what happened: which tool was called, who approved it, and what the system returned. A summary written by the agent cannot replace those records.

Saving task progress is not the same as changing shared knowledge. Review proposed lasting updates for accuracy, access and freshness. Test changes to models, prompts and policies before release.

## The controls, in order

Once the main flow is clear, set the controls for your task. Most are set at the evaluate and approve stages.

1. [The four questions](/architecture/agent-types): what the agent does, what its credentials allow, how freely it acts, and what it can damage.
2. [The autonomy contract](/architecture/autonomy-contract): how freely it may act, and how far its behaviour may learn.
3. [The risk profile](/architecture/risk-profile): score the agent to set its risk tier. The tier decides the controls.
4. [The deterministic zones](/architecture/deterministic-zones): access, money, safety actuation and formal regulatory records. A model never approves in these.
5. [The delegation chain](/architecture/delegation-chain): trace every action back to the person who asked.
6. [Enforcement outside the model](/architecture/enforcement): where each check sits and who runs it.
7. [The learning flywheel](/architecture/learning-flywheel): how a proposed improvement is tested before it ships.

## Evidence and limits

This is a reference design, not a product to buy. The three-part frame is this guide's own. The lifecycle stages follow AWS and Microsoft guidance closely. The capability names follow AWS, Microsoft and Google products, dated on [What an agent platform provides](/architecture/system-view). The inspection example is a proposed design. It is not a measured deployment.
