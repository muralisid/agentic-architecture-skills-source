A rule written in a prompt is a request. The model may follow it, or a crafted document may talk it out of it. The same rule, checked by a separate system the model cannot argue with, is a control. So the rules that bind an agent are enforced outside the model, in three places. The first is the gateway that every tool call passes through. The second is the policy decision point, which says yes or no to each consequential action. The third is a set of fixed rules promoted from what the agent learned, after testing and approval. Two of [the seven capabilities](/architecture/system-view) an agent platform provides do this work: the tool gateway, and identity and policy.

## What a model can be talked into

A <Term k="model">model</Term> reads its instructions and the content it works on as one stream of text. Training alone cannot teach it to keep the two apart. So text inside an email, a web page or a ticket can steer it. EchoLeak showed this in 2025. A crafted email made a <Term k="retrieval">retrieval</Term> agent send company data out, with no click from the user. It scored 9.3 out of 10 on the standard severity scale (CVE-2025-32711). So the checks that matter sit outside the model.

## Enforcement point 1: the gateway

Every <Term k="tool">tool</Term> call passes through the <Term k="gateway">tool gateway</Term>. It is the single door between agents and the systems they touch. It keeps a list of allowed tools and checks that no tool's description has changed. It swaps in the identity of the person who asked, using <Term k="token exchange">token exchange</Term>. It adds credentials at the last moment, so the agent never holds secrets. It limits how often each tool is called, and it records every call.

Approval rules may be written in the <Term k="harness">harness</Term>, the engineering shell around the model. Only the harness sees the whole task. But the rules are enforced at the gateway, because the gateway cannot be talked out of them. The gateway is built in the [integration fabric layer (R03)](/layers/r03-integration-fabric).

## Enforcement point 2: the policy decision point

The <Term k="policy decision point">policy decision point</Term> sits in the path of every tool call. It checks fixed rules against who is asking and what they want to do. Then it says yes or no. It checks every consequential action, and it fails closed: if it is down, the answer is no.

Two kinds of rules engine are common. Cedar-style engines answer in under a millisecond, and their logic is formally verified. They hold no state between calls. Open Policy Agent style engines handle rules that join data from several sources.

Speed matters here. A policy engine answers in a millisecond or a few. A guardrail that calls a large language model takes about 1.5 seconds. That is about a thousand times slower, on every action, for as long as the agent runs.

Two newer checks can sit beside it. The first tracks data from untrusted sources and blocks any flow the policy forbids. One such tool, FIDES, stopped every policy-breaking injection on a standard test set [vendor]. Its own documentation still calls it experimental (October 2026). The second verifies outputs with formal logic. AWS Automated Reasoning checks have been generally available since August 2025 [vendor].

## Enforcement point 3: promoted rules, landed outside the model

An agent can learn a rule from its own work. That rule counts only after it passes [the learning flywheel](/architecture/learning-flywheel). It must survive <Term k="counterexample">counterexamples</Term>, which are test cases built from real failures. It must not make any existing <Term k="eval">eval</Term> worse. A person must approve it. Then it is written as <Term k="policy-as-code">policy-as-code</Term>, versioned and deployed apart from the model. A rule the model only reads is still a request.

This has a ceiling. One study read real agent instruction files statement by statement. About a quarter of the statements could be checked by a fixed rule as written. The other 74 percent depended on context nobody can define in advance. That is why the gateway and the policy decision point carry most of the load.

## What guardrails are for

A <Term k="guardrail">guardrail</Term> is a filter, often a model itself, that screens what goes into or comes out of an agent. Guardrails are an early warning. They are never the lock. Attackers get past them often, and attacks tuned to a defence get past more. Guardrails still help with content policy, spotting personal data, and monitoring, where a miss can be tolerated.

Watch a guardrail's block rate in both directions. A spike suggests an attack. A drop suggests a broken setting. The measured bypass rates are in Evidence and limits below.

## The ten guardrail categories

No single industry list of guardrails exists. But the 2026 guidance from regulators and security agencies shares one shape. Bound the agent by design. Enforce approval and limits outside the model. Isolate where code runs. Monitor, and keep a stop switch. This guide groups the controls they name into ten categories. Seven are fixed rules. Input, output and monitoring also use model checks.

1. **Input.** Treat outside content as untrusted. Keep instructions apart from data. Use typed formats between agents. Injection classifiers add a model check.
2. **Output.** Mask known patterns, such as card numbers. Use data loss prevention. Check that answers are grounded and citations resolve. An output takes the highest data class of its inputs. Validate before display. Grounding checks use a model.
3. **Tool and action.** Allow only listed tools, with pinned versions. Use strict input formats. Put a policy decision point on each call, failing closed. Write destructive actions as separate rules. Keep reading and acting roles apart.
4. **Identity and access.** Give each agent its own identity. Use short-lived, scoped credentials. Use <Term k="just-in-time access">just-in-time access</Term> for high-impact actions. The agent gets the lesser of its own rights and the user's. It never grants itself access. A proxy injects credentials.
5. **Data and egress.** Deny network access by default. Allowlists name operations, not just domains. An outbound proxy checks identity. Public-facing agents stay away from internal data. Data is routed by its class.
6. **Spend and rate.** Set caps per run and per agent. Limit rates and retries. Add circuit breakers at agent, workflow and business-unit level. Cap payment mandates.
7. **Runtime isolation.** Run any code in a <Term k="sandbox">sandbox</Term>. Untrusted code that touches sensitive data gets stronger, hypervisor-level isolation. Allow no network by default and no production credentials.
8. **Monitoring and kill switch.** Keep logs the agent cannot change. Add anomaly detection and watcher agents, which use models. Place a <Term k="kill switch">kill switch</Term> in identity, gateway, runtime and harness. Keep a way back to manual operation.
9. **Change control.** Version and approve prompts, tools, policies, models and memory rules. Red-team after a major change. A listed change re-runs the tests.
10. **Human oversight.** Designers, not the agent, set checkpoints for high-stakes, irreversible and unusual actions. Approval is bound to the exact action. If the approval system fails, the answer is no. One approval covers one bounded action. [The deterministic zones](/architecture/deterministic-zones), the destruction rule and the rule for decisions about people sit here.

A model-based check may warn or take permission away. It never stands alone between an agent and an irreversible effect.

## Which categories apply at each risk tier

How much of each category an agent needs depends on its risk tier, set on [the risk profile](/architecture/risk-profile). The tier is fixed when the agent is approved in [the agent lifecycle](/architecture/agent-lifecycle). There are three tiers: Tier 1 (basic), Tier 2 (enhanced) and Tier 3 (strict). Each keeps everything in the tier below and adds to it. What the agent can do also switches categories on. The last column names those triggers.

Three terms appear in the table. The agent's own identity (ID2) means its own account, least privilege, short-lived credentials and a named sponsor. [The delegation chain](/architecture/delegation-chain) sets out that scale. The Rule of Two is Meta's test (31 October 2025). An agent should combine at most two of three things. They are untrusted input, sensitive data, and the power to change something or send data out. Plan-then-apply means the agent proposes a change, and a fixed system applies it after approval.

| Category | Tier 1 (basic) | Tier 2 (enhanced) adds | Tier 3 (strict) adds | Switched on by |
|---|---|---|---|---|
| Input | Untrusted content marked | Injection classifier as a signal | Rule of Two check at session start | Untrusted input; browsing |
| Output | Data loss prevention; data class carried to outputs | Grounding check; citations resolve | Validation before display | Sensitive data; external messages |
| Tool and action | Allowlist with versions | Policy decision point on every write | Policy decision point on every action; plan-then-apply | Writes; deletes; actions in a zone |
| Identity and access | The agent's own identity (ID2); short-lived credentials | The user's identity carried through | Just-in-time access per high-impact action | Access changes; sub-agents |
| Data and egress | Network denied by default | Outbound proxy that checks identity | Routing by country where the data class needs it | Browsing; external messages |
| Spend and rate | Cap per run | Budget per agent | Circuit breakers by business unit | Payments; long loops |
| Runtime isolation | Sandbox if code runs | Same | Hypervisor-level isolation | Code or database queries |
| Monitoring and kill switch | Logs; kill switch | Kill switch drilled and timed | Continuous monitoring | Agents that start on their own |
| Change control | Listed changes re-run the evals | Red team after a major change | Independent validation | Memory writes |
| Human oversight | Sampled review | Approval for irreversible actions | A named person approves each zone action, production delete and decision about a person | Payments; equipment; decisions about people |

## The map

Each kind of rule has one place where it is enforced. Each also has a place where people wrongly assume it is.

| What | Where it is enforced | Where it is not |
|---|---|---|
| Tool access and credentials | The gateway | Prompt instructions |
| Approval of consequential actions | The policy decision point, in the tool-call path | The model's judgement, or guardrails |
| Promoted rules about behaviour | Policy-as-code, outside the model | Instruction files the model reads |
| Number of steps, cost and running time | Harness caps plus platform hard caps that stop the run | The model holding itself back |
| Content policy and personal data screening | Guardrails, as advice | Anything consequential |

## A worked example: a billing correction at a utility

A utility's billing agent proposes a corrected bill after a wrong meter read. The call goes to the billing system through the gateway. The gateway checks that this tool is on the agent's list. It adds a short-lived credential tied to the agent's identity, and it logs the call. The policy decision point then applies the rule. Is the confidence above the agreed level, and is the change under the hard limit? If yes, the bill is released, and a sample is checked later. If no, a specialist decides.

Suppose the agent notices that estimated reads after a meter swap are often wrong. That lesson does not change the agent's behaviour on its own. It becomes a fixed rule only after it passes the tests and a person approves it. The full design is on [billing exceptions](/use-cases/billing-exceptions).

## Evidence and limits

The three enforcement points follow 2026 guidance from regulators and security agencies. Six sources say model-based guardrails reduce risk but do not authorise anything. They are IMDA, the UK NCSC, the Five Eyes agencies, AWS, OWASP and Anthropic.

In published tests, about three in four attacks got past three named commercial guardrail products. One October 2025 study broke 12 published defences, most at above 90 percent, once attacks adapted.

There are fair counterpoints. IMDA and Google keep model checks where fixed rules cannot define the risk, such as harmful content. AWS lets a guardrail score feed a policy decision [vendor]. The ten categories and the tier matrix are expert judgement. No study links any tier or category to incident rates.
