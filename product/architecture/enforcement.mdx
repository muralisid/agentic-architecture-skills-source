<PlainTerms>
An AI model can be talked into things, because the instructions it follows and the content it reads arrive through the same channel. So the rules that matter, such as who may access what and which actions need approval, are enforced by separate components that the model cannot argue with. This page shows the three places those controls live, and why AI-based filters are an early warning rather than the lock on the door. The one thing to remember: a rule the model merely reads is advice; a rule enforced outside the model is a control.
</PlainTerms>

## Why enforcement must sit outside the model

**WHY:** The model receives instructions and untrusted content through the same language channel, so its behaviour can be manipulated by what it reads. A prompt can express intent, but it cannot guarantee authorization. AI guardrails remain useful detectors, but measured bypass rates and their latency make them the wrong final decision-maker for consequential actions.

**WHAT:** Enforce in three external tiers. **Tier 1: the gateway** controls tool reachability, identity exchange, credentials, rate limits and logging. **Tier 2: a deterministic policy decision point** says yes or no to consequential actions. **Tier 3: learned rules become real only after testing, human approval and promotion into policy-as-code outside the model.** Keep guardrails as advisory detection and content-policy components.

## The premise

**In short:** The model's behaviour can be manipulated through what it reads, so behaviour cannot be the foundation of a control.

An <Term k="agent">agent</Term>'s behaviour is the output of a <Term k="model">model</Term>, and the model's inputs can manipulate it. That makes behaviour the wrong foundation for a control. A model processes commands and content as one undifferentiated stream of text (token-uniform processing), so training alone cannot teach it to keep the two apart. Without a control that sits outside the model, authorization turns into a hunt for the next exploit. EchoLeak proved the class. It is catalogued as CVE-2025-32711 (Common Vulnerabilities and Exposures) and scored 9.3 on the 10-point Common Vulnerability Scoring System (CVSS). It exfiltrated data, pulling it out of the organisation through a <Term k="retrieval">retrieval</Term> agent without the user clicking anything, working entirely in natural language. So enforcement lives outside the model, in three tiers.

## Tier 1: the gateway

**In short:** Every request an agent makes to a tool goes through one door, and that door does the checking.

Every <Term k="tool">tool</Term> call passes through the <Term k="gateway">gateway</Term>, the single door between agents and the systems they touch. The gateway applies an allowlist of permitted tools, exchanges the caller's identity (<Term k="token exchange">token exchange</Term>), and injects credentials. It also checks that each tool's description has not changed, applies rate limits, and records every call for audit. Approval rules may be held in the <Term k="harness">harness</Term>, the engineering shell around the model, because only the harness sees the whole loop. They are enforced at the gateway, because only the gateway cannot be talked out of them. Full detail is on [the R03 page](/layers/r03-integration-fabric), which covers the integration fabric.

## Tier 2: the policy decision point

**In short:** A fixed-rules component says yes or no to every consequential action, about a thousand times faster than an AI filter.

A <Term k="deterministic">deterministic</Term> <Term k="pdp">policy decision point (PDP)</Term> sits in the tool-call path. It is the component that says yes or no to an action by checking rules against who is asking, and it is evaluated on every consequential action. Two engine families offer a real trade-off. Cedar-class engines answer in under a millisecond and are formally verified, but they are stateless. Open Policy Agent (OPA) class engines handle richer joins across data. Two complements apply where the workload warrants them, and they differ in maturity. The first is deterministic information-flow control: FIDES, in a major agent framework, scored zero policy-violating <Term k="injection">injections</Term> on the AgentDojo <Term k="benchmark">benchmark</Term>, against 20 to 152 without it [vendor]. Its own documentation (October 2026) marks it experimental and Python-only, not supported where code executes, and silent on file and network capabilities. Where code runs, the sandbox, egress and credential layers carry the load. The second is formal output verification: Automated Reasoning checks, generally available (GA) since August 2025 [vendor].

The cost argument is decisive on its own. A policy-engine evaluation takes under a millisecond to a few milliseconds. A <Term k="guardrail">guardrail</Term> call that uses a large language model (LLM) takes around 1.5 seconds. That is a difference of roughly a thousand times (three orders of magnitude), paid on every action, forever.

## Tier 3: promoted rules, landed outside the model

**In short:** A rule an agent learns only counts once it has passed testing and been written into policy outside the model.

Learned behaviour graduates into enforcement only through the <Term k="flywheel">learning flywheel</Term> gate. The rule must survive <Term k="counterexample">counterexamples</Term> (test cases built from real failures), pass <Term k="eval">eval</Term> regression (the standing test suite), and receive human approval. The <Term k="promotion">promoted</Term> artifact then lands in <Term k="policy-as-code">policy-as-code</Term>, versioned and deployed independently of the model. A rule the model merely reads is still a soft rule. The ceiling on such rules is measured. A statement-by-statement analysis of real agent instruction files found roughly a quarter of statements enforceable by a fixed check as written. It found 74 percent depending on context that cannot be defined in advance. Formal work adds a second limit. Deterministic gates can enforce strictly less than edit automata, a more powerful class of enforcement monitor, so some rules about behaviour over time (renewal properties) stay out of reach. That ceiling is why tiers 1 and 2 exist.

## What guardrails are for

**In short:** AI-based filters are a useful early warning, but attackers get past them most of the time, so they decide nothing that matters.

Guardrails are the advisory layer, never the boundary. In published tests, roughly 72 percent, 77 percent, and 72.5 percent of attacks got past three named commercial guardrail products, and up to 100 percent got past some configurations. Adaptive attacks do worse to them. An October 2025 study (arXiv 2510.09023) broke 12 published defences, most at above 90 percent, and human red-teamers beat every one. NIST's agent-hijacking evaluations rose from 11 percent to 81 percent success once the attacks were tuned to the defence (January 2025). Vendor figures on fixed benchmarks run far lower, and both kinds of number are reported here so the gap is visible. The only configuration with a measured 0 percent bypass rate paid for it with 16.22 percent false positives and about 1.5 seconds of added <Term k="latency">latency</Term> (delay) per call. A guardrail can also be made to deny service, and that denial is itself exploitable. Guardrails retain genuine value for content policy, detection of personally identifiable information (PII), and <Term k="telemetry">telemetry</Term>, where a miss is tolerable. Their block rate is monitored in both directions: a spike signals an attack, a drop signals misconfiguration.

## The guardrail list, in ten categories

**In short:** There is no single industry list, but 2026 guidance shares one shape, and seven of its ten categories are fixed rules.

**WHY:** No industry-wide guardrail list exists. The 2026 guidance shares a shape instead: bound the agent by design, enforce approval and limits outside the model, isolate execution, monitor, and keep a stop switch.

**WHAT:** This guide groups the controls those sources name into ten categories. In the type column, D means deterministic, M means model-based, and H means hybrid.

| Category | Guardrails | Type | Sources |
|---|---|---|---|
| 1. Input | Outside content treated as untrusted; instructions kept apart from data; typed formats between agents; injection classifiers | D; classifiers M | OWASP cheat sheet; IMDA; Microsoft CAF [vendor]; ASD ISM (secondary) |
| 2. Output | Pattern-based masking; data loss prevention (DLP); grounding checks; citations must resolve; outputs inherit the highest input data class; validation before display | D; grounding M; validation H | AWS Bedrock Guardrails [vendor]; Microsoft CAF [vendor] |
| 3. Tool and action | Allowlisted tools with pinned versions; strict input formats; a policy decision point on each call, failing closed; destructive verbs as separate rules; separate reading and acting roles | D | AWS AgentCore Policy [vendor]; OWASP; Five Eyes |
| 4. Identity and access | One identity per agent; short-lived scoped credentials; just-in-time access for high-impact actions; the lesser of user and agent rights; no self-granting; credentials injected by a proxy | D | Five Eyes; UK NCSC; ASD ISM (secondary) |
| 5. Data and egress | Default-deny network; allowlists that name operations, not just domains; an authenticating egress proxy; public agents kept away from internal data; routing by data class | D | UK NCSC; Microsoft CAF [vendor]; MAS |
| 6. Spend and rate | Per-run and per-agent caps; rate and retry limits; circuit breakers at agent, workflow and business-unit level; payment mandate caps | D | EY (1 June 2026); AWS AgentCore Policy [vendor]; Stripe [vendor] |
| 7. Runtime isolation | A sandbox for any code; hypervisor-class isolation for untrusted code with sensitive data; no network by default; no production credentials | D | UK NCSC; Claude Code and Codex docs [vendor] |
| 8. Monitoring and kill switch | Logs the agent cannot change; anomaly detection; watcher agents; a kill switch in identity, gateway, runtime and harness; return to manual operation | D; anomaly and watchers M | UK NCSC; MAS; NIST AI 600-1; Five Eyes |
| 9. Change control | Versioned, approved prompts, tools, policies, models and memory policy; red-team after a major change; change triggers | D, with a human gate | MAS; Microsoft CAF [vendor] |
| 10. Human oversight | Checkpoints for high-stakes, irreversible and outlier actions, set by designers, not the agent; approval bound to the exact action; deny if the approval system fails; one bounded action per approval; the people-decisions floor | D gate, human judgement | IMDA section 2.2.2; Five Eyes |

This guide's position: seven of the ten categories are deterministic. They are tool and action, identity and access, data and egress, spend and rate, runtime isolation, change control, and human oversight. Input, output and monitoring mix fixed rules with model checks. **A model-based layer may inform or take permission away, but it never stands alone between an agent and an irreversible effect.**

Six sources say model-based guardrails reduce risk but do not authorise. They are IMDA (20 May 2026), the UK NCSC (20 August 2026), the Five Eyes agencies (1 May 2026), AWS AgentCore Policy [vendor], OWASP's AI agent security cheat sheet, and Anthropic's Claude Code documentation [vendor]. There are honest counterpoints. IMDA and Google keep model checks where fixed rules cannot define the risk, such as harmful content. AWS lets a guardrail score feed a policy decision. OpenAI's Agents SDK guardrails do not cover its built-in shell, computer and patch tools [vendor]. That shows why a guardrail inside a software development kit is not a boundary. The destruction rule and the people-decisions floor are set out on [the deterministic zones page](/architecture/deterministic-zones).

## Which guardrails apply, by tier and by capability

**In short:** The risk tier sets how much of each category an agent needs, and what the agent can do switches categories on.

The three tiers come from [the risk profile](/architecture/risk-profile): Tier 1 Basic, Tier 2 Enhanced and Tier 3 Strict. Each tier keeps everything in the tier below and adds to it. The last column names the capabilities that make a category apply.

| Category | Tier 1 Basic | Tier 2 Enhanced adds | Tier 3 Strict adds | Switched on by |
|---|---|---|---|---|
| Input | Untrusted content marked | Injection classifier as a signal | Rule of Two check at session start | Untrusted input; browsing |
| Output | DLP; data class inheritance | Grounding; citations resolve | Validation before display | Sensitive data; external messages |
| Tool and action | Allowlist with versions | Policy decision point on every write | Policy decision point on every action; plan-then-apply | Writes; deletes; zone actions |
| Identity and access | Own identity (ID2); short-lived credentials | User identity carried through | Just-in-time access per high-impact action | Access changes; sub-agents |
| Data and egress | Default-deny network | Authenticating proxy | Sovereign routing where the data class needs it | Browsing; external messages |
| Spend and rate | Per-run cap | Per-agent budget | Circuit breakers by business unit | Payments; long loops |
| Runtime isolation | Sandbox if code runs | Same | Hypervisor-class isolation | Code or SQL |
| Monitoring and kill switch | Logs; kill switch | Kill switch drilled and timed | Continuous monitoring | Self-started agents |
| Change control | Change triggers re-run evals | Red-team on major change | Independent validation | Memory writes |
| Human oversight | Sampled review | Approval for irreversible actions | A named person approves each floor action | Payments; actuation; people decisions |

A few terms. ID2 is this guide's identity floor: the agent has its own account, least privilege, short-lived credentials and a named sponsor ([the identity chain](/architecture/identity-chain)). The Rule of Two is Meta's test (31 October 2025): an agent should combine at most two of untrusted input, access to sensitive data, and the ability to change state or send data out. Floor actions are those covered on [the deterministic zones page](/architecture/deterministic-zones): zone actions, production deletions under the destruction rule, and significant decisions about a person. Plan-then-apply means the agent proposes and a deterministic system applies after approval.

This matrix is this guide's position. It is expert judgement: no study links any tier or capability to incident rates.

## The map

**In short:** Each kind of rule has one place where it is enforced, and a place where people wrongly assume it is.

| What | Where enforced | Where it is not |
|---|---|---|
| Tool access, credentials | Gateway | Prompt instructions |
| Authorization of consequential actions | PDP in the tool-call path | Model judgment, guardrails |
| Promoted behavioural rules | Policy-as-code, out of model | Instruction files the model reads |
| Iteration count, cost, wall-clock time | Harness caps plus platform hard caps (429 too-many-requests on exhaustion) | Model self-restraint |
| Content policy, PII screening | Guardrails, advisory | Anything consequential |
