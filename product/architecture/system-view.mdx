An agent does not live inside one AI model. To finish a task, it reaches into identity, data, applications, tools, records and people. So what must exist before agents can run safely at scale? Seven capabilities. Three let agents work: a runtime, a tool gateway, and [knowledge and memory](/memory). Four keep them in bounds: identity and policy, evaluation and release, observability and an audit trail, and human oversight. You build them across [the fourteen layers](/layers) you already own. Each stage of [the agent lifecycle](/architecture/agent-lifecycle) calls on some of them. Two rules hold them together. [Policy is enforced outside the model](/architecture/enforcement). The audit trail is written where the agent cannot touch it.

## The seven capabilities

The industry already has names for six of the seven. AWS, Microsoft and Google sell them as separate products. The grouping into seven is this guide's own. It lets you point each capability at a product you may already buy. Human oversight is the one no vendor sells. It comes from regulation and from how you organise people.

<GuideFigure id="seven-plane-architecture" fullWidth />

### Runtime

The runtime is where agents run. It holds the <Term k="sandbox">sandboxes</Term>, the sessions that survive a pause, and model serving. A sandbox is an isolated space where an agent's code and tools run. The [infrastructure and compute layer (R01)](/layers/r01-infrastructure) and the [agent platform layer (R07)](/layers/r07-agent-platform) build it. The operate stage calls on it for every run. AWS sells it as AgentCore Runtime. Google calls it Agent Runtime. Microsoft Foundry runs hosted agents on its own Agent Runtime.

### Tool gateway

The tool gateway is how agents reach your systems. Every tool call passes through one gateway, under the agent's own identity. Each tool wraps an existing system behind a governed interface. The gateway also holds the boundary with operational technology (OT), the systems that run physical plant. Agents stay on the information side of that boundary. Three layers build it: [integration fabric (R03)](/layers/r03-integration-fabric), [systems of record (R04)](/layers/r04-systems-of-record), and [line of business and OT (R05)](/layers/r05-lob-and-ot). The operate stage calls on it. AWS sells AgentCore Gateway. It turns existing APIs into <Term k="mcp">Model Context Protocol (MCP)</Term> tools. Google sells Agent Gateway. Microsoft Foundry puts tools in Toolboxes behind one managed endpoint. Analysts call the wider category an AI gateway.

### Knowledge and memory

Knowledge and memory is what agents know. It covers governed indexes, sources curated for a purpose, and memory that lasts beyond one task. Each source keeps its permissions. An agent finds only what its user may see. The [data platform layer (R02)](/layers/r02-data-platform) and the [agent data engineering layer (R14)](/layers/r14-agent-data-engineering) build it. The operate stage calls on it whenever an agent needs context. AWS sells AgentCore Memory. Google offers Sessions and Memory Bank. Microsoft's adoption guidance names retrieval and memory as building blocks. [The data-to-memory pipeline](/architecture/data-to-memory) traces data from its source to a cited answer.

### Identity and policy

Identity and policy decide who the agent is and what it may do. Each agent gets its own identity. A <Term k="registry">registry</Term> lists every agent with its owner, purpose, permissions and live version. A policy decision point says yes or no to each action. Budgets cap what each agent may spend. Three layers build it: [security and identity (R10)](/layers/r10-security-and-identity), [governance, risk and sovereignty (R11)](/layers/r11-governance-risk-sovereignty), and the agent platform (R07). The register, entitle and retire stages call on it. So does approve. It sets the permissions the agent goes live with. [The delegation chain](/architecture/delegation-chain) traces each action back to the person who asked. AWS sells AgentCore Identity, AgentCore Policy and AWS Agent Registry. Microsoft Entra Agent ID gives each agent its own identity. Microsoft Agent 365 adds a registry and access control across agents.

### Evaluation and release

Evaluation and release is how behaviour changes safely. Evaluations (<Term k="evals">evals</Term>) test each change against a fixed set of cases. Judges score the answers. A judge is a model or a person that grades output against a rubric. A promotion gate decides whether the change ships. Release is staged: a small share of work first, then more. This is a <Term k="canary">canary release</Term>. The [intelligence and learning layer (R06)](/layers/r06-intelligence-and-learning) and the [observability and FinOps layer (R12)](/layers/r12-observability-and-finops) build it. The evaluate and change stages call on it. AWS sells AgentCore Evaluations and AgentCore Optimization. Google files this work under its Optimize pillar. Microsoft Foundry lists evaluate and optimize steps. [The learning flywheel](/architecture/learning-flywheel) sets out the gates a change must pass.

### Observability and audit trail

Observability and audit trail is what you can prove afterwards. <Term k="traces">Traces</Term> record each model call, tool call and cost. <Term k="provenance">Provenance</Term> records where each piece of information came from. Retention keeps records as long as the law and the business need them. The observability and FinOps layer (R12) and the governance, risk and sovereignty layer (R11) build it. The operate stage writes to it. The periodic review stage reads from it. AWS, Google and Microsoft all ship agent observability. AWS builds its version on OpenTelemetry, the open standard for traces. Every agent keeps an audit trail baseline. High-risk uses also keep the records Article 12 of the EU AI Act asks for.

### Human oversight

Human oversight is who decides and who answers. It covers supervision, the named people accountable for each agent, and the channels people use. Three layers build it: [operating model and supervision (R13)](/layers/r13-operating-model), [productivity and collaboration (R08)](/layers/r08-productivity-and-collaboration), and [experience and channels (R09)](/layers/r09-experience-and-channels). The sponsor and owner, approve and periodic review stages call on it. No vendor sells human oversight as a product. The term comes from Article 14 of the EU AI Act. Microsoft Entra Agent ID requires a <Term k="sponsor">sponsor</Term> when an agent is created. The sponsor answers for the agent's purpose. [Operate](/operate) shows how to check that people can keep up.

## The two rules

Two rules hold the seven capabilities together. They are also the two most often broken.

**Policy is enforced outside the model.** An instruction in a <Term k="prompt">prompt</Term> is a request. A rule becomes a control when a separate system checks it. That system is the <Term k="gateway">gateway</Term> and the <Term k="policy decision point">policy decision point</Term>. Both sit outside the agent's runtime. The agent cannot go around them. Models may take permission away, never grant it. In the four [deterministic zones](/architecture/deterministic-zones), a model may not approve at all. The four are access, money, safety actuation and formal regulatory records. [Enforcement outside the model](/architecture/enforcement) sets out where each check sits.

**The audit trail is written where the agent cannot touch it.** A log the agent can edit is not proof of what it did. Traces, decisions and provenance go to a store the agent cannot write to. A separate channel collects them as the work happens. Every layer page names where its own checks and records sit.

## One inspection task, seven capabilities

Take an agent that checks vegetation near power lines for an electricity distributor. A person sets the goal: find the spans that need trimming before summer.

1. The runtime starts the agent in a sandbox. It keeps the session if the agent pauses for a photograph.
2. Knowledge and memory supplies the imagery, the asset location and the inspection policy.
3. The tool gateway lets the agent read the asset record and draft a work order.
4. Identity and policy checks each call. The agent may draft a work order. It may not dispatch a crew.
5. Observability and audit trail records each call, each source and each approval.
6. Human oversight puts the draft in front of a planner, who approves or rejects it.
7. Evaluation and release tests any change to the agent before the next season.

This is a design example, not a measured deployment. [The task walkthrough](/architecture/task-walkthrough) follows a similar task step by step.

## Your own agents and vendor-embedded agents

Not every agent passes through your gateway. Agents you build run through your own runtime and gateway. You can see, budget and trace everything they do. Agents embedded in vendor products run on the vendor's platform. Suite copilots and agents inside record systems are examples. Your gateway never sees them. You govern them through the vendor's tenant settings and the activity data the vendor exports. Those exports have documented gaps.

So every design must work for both kinds of agent. A design that assumes one gateway sees everything is the most common structural error at scale. Cost models need the same care. One vendor prices governance per user, and another includes it [vendor pricing]. [Agents and packaged applications](/use-cases/packaged-applications) covers when to wait for the vendor's agent, buy it, or build your own.

## Three kinds of enterprise

The same seven capabilities apply to every enterprise. Who builds them, and in what order, differs.

- **A globally regulated enterprise** runs its own agents and vendor-embedded agents side by side. It keeps one knowledge and memory capability, one registry and one audit trail. Only the enforcement points double: its own gateway, and each vendor's settings.
- **A mid-market company** rents identity and policy from its productivity vendor. It builds knowledge and memory itself. No vendor curates its data for it.
- **A digital-native company** has the runtime and the tool gateway early. It must add identity and policy and an audit trail before autonomy rises. [The autonomy contract](/architecture/autonomy-contract) holds it to that.

## Evidence and limits

The capability names come from vendor documentation read on 15 October 2026. Six of the seven match products that two or three large cloud vendors share. The match is strong for the runtime, the gateway, memory, evaluation and observability. Human oversight has no vendor product. Its anchors are the EU AI Act and Microsoft's sponsor and owner model.

The vendors draw some lines differently. Google files its gateway under governance. AWS files its gateway as a tool service. Microsoft sells Agent 365 as one product for registry, access, observability and security. It spans several of the seven.

The grouping into seven is this guide's own. No standards body groups agent platforms this way. Most vendors use three or four groups, such as build, run, govern and optimise. Seven smaller groups let you check each one on its own.

The two rules match industry practice. Google describes its gateway as a policy enforcement point. AWS checks policy on every tool call at its gateway. Article 12 of the EU AI Act asks high-risk systems to record events automatically. Product status changes fast. Check the dated sources below before you rely on a product name.
