<PlainTerms>
Think of this page as HR (human resources) for agents. Each agent gets its own identity, like a person, and a named sponsor who answers for it. The company can then apply the rules it already has: security policy, access control, change management and approval to production. The rules attach to the role on the identity, not to the product the agent runs on. The one thing to remember: no agent runs without a registry entry and a named sponsor, and no agent is simply switched off and forgotten.
</PlainTerms>

## Why identity alone is not enough

**WHY:** An identity says who the agent is. It does not say who answers for it, or what it may reach. It does not say when its approval goes out of date, or when it should stop. Microsoft's own agent registry shows a standing count of "Agents without owners" [vendor]. Without a lifecycle, agents gather access over time. They outlive their owners. They keep running on approvals given to an older version of themselves.

**WHAT:** Give every agent a registry entry and its own <Term k="agent identity">identity</Term> before it holds any credential. Name a <Term k="sponsor">sponsor</Term> and an owner when the agent is created. Attach a role template and a risk tier to the identity. The enterprise's existing controls then act on that identity. The mechanism is ordinary identity governance. Retirement is a stage with its own steps.

## The nine stages

**In short:** Every agent passes through the same nine stages. Each is marked as shipped in a product, set out in guidance, or this guide's position.

## How the identity and sponsor drive four controls

**In short:** The enterprise already has rules for security, access, change and release. The agent's identity and its sponsor are what let those rules reach the agent.

**Security policy.** Policy targets the agent's own identity, its template, and its registry labels, such as risk tier. One policy on a template covers every agent built from it, including later ones. Microsoft's Conditional Access, its rule engine for sign-in and token decisions, works this way. It can target one agent, its template (Microsoft calls it a blueprint) or a label [vendor]. It cannot protect resources reached with an API key, a fixed secret that grants access (Microsoft Learn, 7 October 2026). So the agent holds no keys. The gateway injects credentials at execution time, as [the identity chain](/architecture/identity-chain) sets out.

**Access control.** The template sets the baseline. Extra access is a narrower grant for a stated task, and every grant expires. In Entra, the sponsor can renew an expiring grant or let it lapse [vendor]. When the agent acts for a person, the lesser right wins. That is either the person's rights or the agent's own grant. The highest data class the agent can reach caps every grant. That cap is this guide's position, because no product does it yet. Microsoft Purview governs what an agent can read. But content an Agent 365 agent creates does not inherit the source's sensitivity label [vendor].

**Change management.** Every change trigger is logged against the agent's registry record. A triggered change re-runs the evals and the risk profile before release. The sponsor is told. No standard defines which changes force re-approval. Practitioners say an approval covers one configuration (NHIMG). Gravitee notes that a model upgrade can pass every old test [vendor]. It can still change which tool the agent picks.

**Approval to production.** The risk tier on the registry record picks the approval path. The three tiers are set out on the [risk profile](/architecture/risk-profile) page. The sponsor and the owner sign at every tier. More signers join at Tiers 2 and 3.

## The change triggers

**In short:** Eight kinds of change make an approval out of date. Each one re-runs the evals and the risk profile before it goes live.

- **Model.** A new model or model version, including a vendor upgrade.
- **Prompt.** The system instructions or any approved prompt template.
- **Tools.** A tool added, removed, or changed in what it can do.
- **Permissions.** Any change to a grant, a scope or a credential.
- **Data sources.** A new source, or a source with a higher data class.
- **Memory policy.** What the agent keeps, for how long, and who can read it.
- **Autonomy level.** Any move on the A0 to A5 scale in [the autonomy contract](/architecture/autonomy-contract).
- **Sponsor.** A new sponsor, including the automatic hand-over to a leaver's manager.

That a new tool grant re-runs the risk assessment is this guide's rule. It is already in the guide's glossary, under capability-surface gating. Each grant changes the agent's <Term k="capability surface">capability surface</Term>. Practitioners and gateway vendors say the same. No standard says it.

How heavy the re-run is depends on the tier. For a low-risk agent it can be an automated pipeline step. For a high-risk agent it goes back through the full approval path.

## Periodic review

**In short:** At each review, the sponsor checks four things: purpose, access, budget and continued need.

Change triggers catch what someone changed. Periodic review catches what drifted. Access goes unused. A purpose goes away. A budget creeps up. A no on any check starts a change or a retirement. Quarterly is this guide's default. The CAF and the AWS lens both name it [vendor]. The [risk profile](/architecture/risk-profile) allows a yearly review for Tier 1 agents.

## Retire, and the orphan problem

**In short:** Stopping an agent is not retiring it. Retirement removes its access, memory and unique tools, and keeps the record of what it did.

AWS's Well-Architected agentic lens names four states: Active, Under review, Deprecated, Decommissioned [vendor]. It flags idle agents by the date they last ran. It warns to check seasonal agents first, such as one that runs only at tax time. This guide calls the last state retired.

1. **Disable.** Stop new work and block new tokens.
2. **Revoke.** Remove every credential, grant and key. Record how long it took.
3. **Redirect.** Send callers and scheduled triggers to a replacement or to a person.
4. **Remove.** Delete the agent's own memory and data. Remove tools that only this agent used. The DTA's agentic addendum lists these removals, read here through a search summary.
5. **Keep.** Keep decision records and traces in the system of record, for audit and legal retention.

In Entra, a sponsor can disable an agent but cannot re-enable it. Only an owner can restore it or delete it for good [vendor].

**Orphans.** An orphan is an agent that keeps running after its owner's account is disabled (Obsidian Security) [vendor]. People leave, and their agents stay. Entra covers the common case: when a sponsor leaves, sponsorship moves to their manager automatically [vendor].

The clearest public case is Moltbook, a social network where AI agents post. Wiz reported on 2 February 2026 that its database exposed about 1.5 million agent API keys. They belonged to about 17,000 human owners, roughly 88 agents per owner. Moltbook was a hobby platform, not an enterprise system. No vendor-neutral data exists on orphan rates, or on how long it takes to revoke an agent.

## The registry record

**In short:** One record per agent holds what the four controls need.

The [registry as compliance inventory](/layers/r11-governance-risk-sovereignty#the-registry-as-compliance-inventory) records owner, purpose, risk tier, tools, credentials, and model and prompt versions. This record separates sponsor from owner. It adds the highest data class and the autonomy the agent actually uses. No vendor documents data class or risk tier as a registry field. The list below is this guide's position.

**Who it is and why it exists**

- **ID and template.** The agent's unique identity and the template it was built from.
- **Purpose.** What the agent is for, in one sentence.
- **Role and domain.** The work it does and the business area it serves.
- **Sponsor.** The accountable business person.
- **Owner.** The technical custodian.
- **Estate.** Whether it runs behind the enterprise's own gateway or inside a vendor product.
- **Origin.** What starts its work: a person, an event, or the agent itself.
- **Lifecycle state.** Active, under review, deprecated or retired.

**What it can do**

- **Credential verbs and scopes.** What its own credentials let it do (read, write, delete, pay, send) and where.
- **Untrusted-input flag.** Whether it reads content from outside the enterprise.
- **Highest data class.** The most sensitive data it can reach. This caps every grant.
- **Egress.** Where it can send data out to.
- **Zones and floors.** Which [deterministic zones](/architecture/deterministic-zones) it works near, and which fixed minimum controls apply.

**How it is governed**

- **Risk tier and the factor that set it.** The tier, and the factor that pushed it there.
- **A-level designed, permitted and exercised.** The autonomy it was built for, is allowed, and actually uses.
- **L-level.** Its learning level, L0 to L3.
- **Budget.** Its spending allowance and hard caps.
- **Eval results.** The latest results, and the version they tested.
- **Approval record.** Who signed, at which tier, for which configuration.
- **Regulatory tags.** The rules that apply, such as a sector regime.

**How it changes over time**

- **Model, prompt and tool versions.** What is live now.
- **Memory policy.** What it keeps, and for how long.
- **Change log.** Every trigger, with its date and outcome.
- **Last review.** The date and result of the last periodic review.
- **Last invocation.** When it last ran. This flags idle agents.
- **Revoke time.** How long the last revoke took.

Three regulators already ask for parts of this record. The Monetary Authority of Singapore (MAS) issued guidelines on 7 October 2026. They want an AI inventory that carries identifiers, tools and guardrails. Australia's Digital Transformation Agency (DTA) policy v2.0 applies from 15 December 2025. It wants a named owner for each AI use case, and a register shared every six months. APRA, Australia's bank and insurance regulator, wrote on 30 April 2026. It expects an inventory, and ownership "from design and development through to deployment". It named decommissioning of AI as a weak area.

## The words this guide uses

- **Sponsor** is the accountable business person. Microsoft uses the word this way. The DTA's own register uses "executive sponsor".
- **Owner** is the technical custodian. Okta, Ping, SailPoint and others use "owner" for the accountable person. Read their "owner" as this guide's sponsor.
- **Registry** is the record of agents. It is the most common term across vendors.
- **Retire**, not decommission. The word is plainer.
- **Periodic review**, not attestation. On this site, attestation means a named person signing a formal record in [the records zone](/architecture/deterministic-zones#formal-regulatory-records).

## Evidence and limits

The strongest evidence here is Microsoft's own documentation. It is vendor material, describing one vendor's design. The regulators (APRA, the DTA and MAS) say what to keep and who must own it. None names agent risk tiers or a field list.

Four gaps matter. No vendor documents data class or risk tier as a registry field, so the record above is this guide's design. No standard defines what change forces re-approval. No vendor-neutral data exists on orphan rates or time to revoke. No incident data exists to test any stage against.

The DTA pages timed out and were read through search summaries. The AWS Agent Registry, SailPoint, CyberArk and Okta dates came from summaries or trade press. Re-check every date before relying on it.
