An agentic enterprise is a company where governed <Term k="agent">agents</Term> do the routine knowledge work. People set the intent, supervise the work and handle the exceptions. They stay accountable for the result. Picture a modern bottling plant. The line runs on its own, and a few skilled people step in when a machine jams. Knowledge work is heading the same way. Three ideas frame the guide: [layers you own](/layers), [a lifecycle you run](/architecture/agent-lifecycle), [capabilities you add](/architecture/system-view). You already own fourteen layers of systems, from infrastructure to agent data. Every agent passes through one lifecycle, from register to retire. You add seven capabilities across the layers so agents can run safely. This page puts the guide into seven steps. Each step lists the pages to read, in order. Each ends with a gate: what must be true before you move on.

## What changes

"Today" means how most companies work now, including their first agent pilots.

<TeachingIllustration src="/figures/start/what-changes.svg" mobileSrc="/figures/start/what-changes-mobile.svg" expandable title="What changes" alt="Six rows compare today with the agentic way. Routine work moves from people to governed agents, each with its own identity. People set intent, supervise, handle exceptions and stay accountable. Rules move from the prompt to the gateway and the policy decision point. The audit trail is written where the agent cannot touch it. A change ships only after it passes evals, not when someone edits a prompt. The same fourteen layers stay. Seven capabilities are added across them, and every agent runs through one lifecycle." caption="Violet marks the work agents do. Amber marks what people do. The layers you own stay the same." />

| | Today | Agentic |
|---|---|---|
| Who does routine work | People, with software as a tool | Governed agents, each with its own identity |
| What people do | Carry out each step | Set intent, supervise, handle exceptions and stay accountable |
| Where the rules live | In the prompt | At the gateway and the policy decision point, outside the model |
| Who records what happened | Often the agent, in its own log | An audit trail written where the agent cannot touch it |
| How behaviour changes | Someone edits the prompt | A change ships only after it passes its evals |
| What stays and what is new | The fourteen layers you own | The same fourteen layers, with seven capabilities added across them and a lifecycle for every agent |

The gateway and the policy decision point are services outside the model. They allow or block each action. Evaluations (evals) are fixed tests that a change must pass before release. [Enforcement outside the model](/architecture/enforcement) and [the learning flywheel](/architecture/learning-flywheel) explain both.

## 4. Design

Turn the use case into an agent you can bound.

1. [What kind of agent is this? Four questions](/architecture/agent-types): its role, permissions, autonomy and impact.
2. [The autonomy contract](/architecture/autonomy-contract): the autonomy and learning levels, and the ceiling readiness sets.
3. [The risk profile](/architecture/risk-profile): score the agent to set its tier. The tier sets the controls.
4. [The deterministic zones](/architecture/deterministic-zones): the areas where a model may never approve.
5. [The delegation chain](/architecture/delegation-chain): trace every action to the person who asked.
6. [The agent lifecycle](/architecture/agent-lifecycle): register the agent, name its sponsor and owner, and set what it may reach.
7. [Enforcement outside the model](/architecture/enforcement): where the controls sit.
8. [The data-to-memory pipeline](/architecture/data-to-memory): from company data to a cited answer.
9. [The fourteen layers](/layers): what each part of the estate must provide.
10. [The threat model](/security/threat-model) and [the decision catalog](/decisions): what can go wrong, and the technology choices with verdicts.

**Gate:** the zone register is signed and the controls are chosen. The zone register is the one-page list of who decides in each zone.

## 5. Build

Build the agent and test it before anyone relies on it.

1. [The intelligence ladder](/ladder): the order in which to try changes.
2. [Choose what to change](/ladder/choosing-an-approach): match the change to the failure.
3. [Knowledge and memory](/memory): give the agent the evidence it needs.
4. [The Agentic OS](/agentic-os): the runtime you buy and the harness you build.
5. [Context patterns](/patterns): tested ways to give an agent the right context.
6. [The learning flywheel](/architecture/learning-flywheel): the evals a change must pass.

**Gate:** the evals pass and the approvals are signed.

## 6. Operate

Run the agent, watch it, and count what it costs.

1. [Operate: the weekly loop](/operate): the four checks to run every week.
2. [The observability and FinOps layer](/layers/r12-observability-and-finops): traces the agent cannot forge, and budgets with hard limits.
3. [The operating model and supervision layer](/layers/r13-operating-model): how much supervision the work really needs.
4. [The agent lifecycle](/architecture/agent-lifecycle): the operate, change, periodic review and retire stages.
5. [Measure value and full cost](/use-cases/value-and-investment): compare the result with the old process.
6. [The economics model](/library/architecture/economics-model): the full cost of each outcome.

**Gate:** oversight capacity holds at peak load, not just on an average day. Oversight capacity is how much exception work people can clear in time.

## 7. Scale autonomy

Let a proven agent do more, one level at a time.

1. [The autonomy contract](/architecture/autonomy-contract): the controls and checks that earn each higher level.
2. [The learning flywheel](/architecture/learning-flywheel): improve behaviour without losing control of it.
3. [The risk profile](/architecture/risk-profile): how outside autonomy scales map to this guide's levels.
4. [Build an agentic enterprise](/use-cases/enterprise-transformation): share what works across the company.

**Gate:** each move to a higher level waits until readiness, controls and oversight capacity all allow it.

The next use case starts again at step 3.

## Who owns each step

**A chief information officer (CIO)** owns steps 1, 2 and 7. They set the intent and accept the readiness profile. They decide when an agent may act more freely. They also fund the use cases chosen at step 3.

**An enterprise architect** owns steps 4 and 5. They turn each use case into a designed agent. That means its four answers, its risk tier, its zones and its controls. They make sure the build passes its evals.

**A programme lead** owns steps 3 and 6. They choose the use cases and set up each trial. They run the agents day to day and measure the value. They bring each new use case back to step 3.
