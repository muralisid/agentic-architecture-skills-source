<PlainTerms>
This is prompt writing, and everyone has done some. What most people have not done is treat it as engineering: pinning the output shape so it cannot drift, teaching by example rather than by adjective, and letting a machine search for a better prompt than a person would write. This page covers the mechanics, then applies them to a utility inspection brief. The one thing to remember: you have not exhausted this step until a matched evaluation shows that instruction changes no longer address the observed failure.
</PlainTerms>

## What a prompt is actually made of

A prompt is not one blob of text. It has parts, and each does a different job.

**The system instruction** sets standing rules: who the agent is, what it may and may not do, how it should behave when unsure. It is the same on every call, which matters for cost, as we will see.

**The task instruction** describes this specific piece of work.

**The examples** show completed instances of the task. This is the highest-leverage part and the most underused. A model infers a pattern from two or three good examples far more reliably than from a paragraph describing the pattern. "Write formally" is an adjective and every model interprets it differently. Three samples of your actual house style are unambiguous.

**The input** is the material for this instance.

**The output contract** states the shape you want back, and it should be enforced rather than requested. Modern APIs accept a schema and constrain generation to match it, so the model cannot return prose where you expected fields. Asking politely in the prompt for JSON produces JSON most of the time, which is the worst possible reliability: frequent enough to build on, rare enough to break in production.

## Order matters more than people expect

Put the stable parts first and the varying parts last. Providers cache the unchanging prefix of a prompt, and a cache hit is billed at a fraction of fresh input. Any change anywhere in that prefix invalidates everything after it, so a timestamp near the top of a system instruction quietly destroys the saving on every call.

That single ordering decision is often the difference between an agent that is affordable at volume and one that is not, and it costs nothing to get right.

## Automated optimisation beats hand-tuning

The instinct is to write a prompt, read the failures, and rewrite it. That is a search process run by hand, slowly and with a small sample.

Run it as a search instead. A published method treats prompts as candidates to be mutated and selected: the system reads its own failures, proposes revisions, and keeps a diverse frontier of candidates rather than hill-climbing on one. It beat a reinforcement-learning baseline by six points on average and up to twenty, using up to 35 times fewer rollouts, with gains appearing from as few as ten training examples (GEPA, arXiv 2507.19457, ICLR 2026).

Two things follow. Teams that hand-tune and then conclude the model is the limit have usually not run this, so their ceiling is not the model's ceiling. And ten examples is a low bar, which means this is available long before you have enough data for anything in Model adaptation.

A related result treats context as something that accumulates: rather than one prompt being rewritten, a playbook is grown and curated across many runs. It improved agent benchmarks by 10.6 points and finance tasks by 8.6, with no weight updates and no labelled supervision (ACE, arXiv 2510.04618, ICLR 2026).

A playbook that grows across runs is memory, and it changes how the agent behaves. So each addition passes the same tested gate as any other change before it takes effect. Nothing is kept just because it piled up. [The learning flywheel](/architecture/learning-flywheel) sets out that gate.

## In utilities and mining

Consider a utility inspection assistant. A vague instruction to “summarize the issue” may produce readable prose that leaves out the asset, observation date, source, or unresolved question.

Specify the output: asset identifier, observed condition, evidence references, uncertainty, and recommended next check. Include approved examples of good briefs and counterexamples showing unsupported conclusions. Validate required fields outside the model.

The task remains evidence preparation. A clear instruction does not authorize the agent to operate equipment or certify a condition. Evaluate the brief against representative cases and reviewer effort. The example is a proposed design, not a measured deployment.

## What this step does not fix



Missing knowledge. If the asset history is not in the context, no instruction recovers it, and a model asked to summarise evidence it cannot see will produce a fluent narrative anyway. That is the failure mode to fear here, and it is a [step 2](/ladder/context) problem.

## The test for moving on

**Compare instruction changes against a fixed <Term k="eval">eval</Term> suite and inspect the failures that remain.**

Flat is the signal. Frustration is not. Without a fixed eval you cannot tell a real ceiling from a bad afternoon, and the difference decides whether you are about to spend a quarter's budget for nothing. Use a fixed evaluation set of representative inspection cases, including missing and conflicting evidence.
