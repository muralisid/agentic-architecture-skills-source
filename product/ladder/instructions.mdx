<Slide journey="ladder/instructions" id="in-01">

Step one is the instructions you give an AI model. A system that uses a model to do a job is called an agent. This video treats writing an agent's instructions as engineering. It ends with a clear test for when to move on.

</Slide>

<Slide journey="ladder/instructions" id="in-intro">

When an agent is not good enough, there are several things you can change. Some are worth trying before others. The first three are tried in order, one step at a time. This order is called the ladder. Instructions are step one.

First, we look at what instructions are made of. Next, we see why the order of the parts matters. Then we see how a machine can improve them.

After that, we look at what instructions cannot fix. Last comes the test for moving on to step two.

</Slide>

## What a prompt is actually made of

<Slide journey="ladder/instructions" id="in-02">

Let us start with what instructions are made of. The written instructions you send to a model are called a prompt. A prompt has five parts. Each part does a different job.

The first part is the standing rules. They say who the agent is and what it may and may not do. They do not change from one case to the next.

The second part describes the task. This is the piece of work to be done right now.

The third part is examples. They show the task already done well.

The fourth part is the input. This is the material for this one case. The fifth part sets the shape of the answer you want back.

</Slide>

<Slide journey="ladder/instructions" id="in-03">

Examples are the most useful part of a prompt. A model picks up a pattern from two or three good examples. That works better than describing the pattern in words. Yet examples are the part people use least.

Say you ask a model to write formally. Each model reads the word formally in its own way. Three samples of the writing you want leave nothing to guess.

</Slide>

<Slide journey="ladder/instructions" id="in-13">

Now look at the shape of the answer. Say a prompt just asks for a clear summary. The answers read well. But each one is laid out in a different way.

So the person checking them cannot skim. They have to read every word. The agent saves them no time.

</Slide>

<Slide journey="ladder/instructions" id="in-04">

There are two ways to set the shape of the answer. The first is to ask for a format in the prompt. That works most of the time. The second is to give the model a form with fixed, named fields. That form is called a schema. The model must fill in those fields.

People come to rely on the first way. Then it breaks once the agent is in real use. Modern model services accept a schema and hold the answer to it. So the model cannot send back loose text instead of the fields.

</Slide>

<Slide journey="ladder/instructions" id="in-16">

The prompt should also name two mistakes the model must never make. The first is making a decision that belongs to a person. An agent that decides for people leads them to trust it too much.

The second is a claim with no source. Every claim must come from the material the model was given. Each claim must also say where it came from.

</Slide>

## Order matters more than people expect

<Slide journey="ladder/instructions" id="in-05">

The order of the parts matters too. Some parts never change from one case to the next. These are the standing rules and the examples.

The input changes every time. Put the parts that never change at the start. Put the changing input at the end. Here is why this order matters.

</Slide>

<Slide journey="ladder/instructions" id="in-21">

The companies that run models keep a copy of the start of each prompt. The next prompt may start in exactly the same way. Then they reuse that stored copy. This is called caching.

Reusing the stored copy costs a fraction of the normal price. So a prompt that always starts the same way costs less.

</Slide>

<Slide journey="ladder/instructions" id="in-06">

The saving only works if the start stays exactly the same. A change anywhere in it breaks the reuse.

Some prompts put today's date and time near the top. This is called a timestamp. It changes every time. So the start of the prompt is never the same.

Everything after the timestamp is charged at full price again. That costs money on every use. Putting the parts in the right order costs nothing.

</Slide>

## Let a machine improve the prompt

<Slide journey="ladder/instructions" id="in-22">

Next, how do you make a prompt better? The usual way is to write it, see where it went wrong, and rewrite it. Most people do all of this by hand.

This is really a search for a better prompt. Done by hand, that search is slow. It also looks at only a few cases.

</Slide>

<Slide journey="ladder/instructions" id="in-07">

A published method lets a machine run this search instead. First, it tries the prompt and reads where it failed.

Then it writes new versions of the prompt. It keeps a varied set of good versions instead of polishing only one. Then it goes round again.

</Slide>

<Slide journey="ladder/instructions" id="in-08">

This method has been tested in published research. It did better than a method that retrains the model itself.

It also needed very little to get started. Its results improved with as few as ten sample cases to learn from.

</Slide>

<Slide journey="ladder/instructions" id="in-09">

Two things follow from this. First, some teams improve a prompt by hand and then blame the model. Most of them have not run this kind of search. So they have not seen what the model can really do.

Second, ten cases is a small number. You will have ten cases long before you have enough data to change the model.

</Slide>

<Slide journey="ladder/instructions" id="in-10">

A related method does not rewrite one prompt. Instead, it keeps a written set of lessons for the agent. The set grows and is tidied each time the agent does its job. This set of lessons is called a playbook.

In published tests, a growing playbook improved results. It did not need to train the model. It also did not need correct answers written out in advance.

</Slide>

<Slide journey="ladder/instructions" id="in-11">

An agent can keep things and use them again later. What it keeps is called memory. So a growing playbook is memory. It changes how the agent behaves.

That is why each new lesson is tested before the agent uses it. It gets the same checks as any other change. Nothing is kept just because it piled up.

</Slide>

## What this step does not fix

<Slide journey="ladder/instructions" id="in-18">

Even good instructions have a limit. If a fact is not in what the model can see, no instruction can supply it.

The model will still write an answer that sounds confident. That is the failure to watch for at this step. Step two, context, is about what the model gets to see. That is where this problem gets fixed.

</Slide>

## The test for moving on

<Slide journey="ladder/instructions" id="in-19">

Now, how do you know when this step is done? You need a set of test cases that never changes. This is called a locked test. Without it, you cannot tell if the prompt has really stopped improving.

Use past cases where you already know the right outcome. Score every change to the prompt against them.

</Slide>

<Slide journey="ladder/instructions" id="in-20">

Here is the test for moving on. Spend a focused week improving the prompt against the locked test. If the score climbs and then goes flat, this step is done. Feeling stuck is not enough on its own.

Then move on to [step two](/ladder/context), context.

</Slide>

## What to remember

<Slide journey="ladder/instructions" id="in-recap">

Here is what to remember from step one. Show the model good examples. Hold the shape of the answer with a schema. Put the parts that never change at the start of the prompt. Let a machine search for a better prompt.

Instructions cannot supply facts the model cannot see. Move on when a week of work stops moving the score on a locked test. Next is step two, context.

</Slide>
