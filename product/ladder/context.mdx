<PlainTerms>
This step decides what the model gets to see. Documents are cut up, turned into numbers, stored, and searched. Every one of those choices changes the answer, and on our own measurements they change it more than anything else available. This page explains the pipeline, the failure that catches almost everyone, what changes when the agent keeps memory, and what it looks like inside a bank. The one thing to remember: a document about several things gets one average summary, and a question about one of those things then matches it only weakly.
</PlainTerms>

## The pipeline, in order

**Parse.** Turn the source file into text while keeping its structure. A table that becomes a run-on sentence has lost the relationship between a figure and its label, and no later stage recovers it. Parsing quality sets the ceiling for everything downstream, so it gets spot-checked forever rather than assumed.

**Chunk.** Split into retrievable pieces. Too large and one piece covers several topics. Too small and a piece loses the context that made it meaningful. No single recipe survives across corpora, which is why this is evaluated rather than configured.

**Embed.** Turn each piece into a vector: a list of numbers positioning it in a space where nearby means similar in meaning. Every vector carries the version of the model that produced it, because changing encoder invalidates the whole index.

**Index.** Store the vectors for fast nearest-neighbour search, and store the source's access rights alongside them.

**Retrieve.** Turn the question into a vector the same way, find the nearest pieces, and pass them to the model.

## The failure that catches almost everyone

Embedding a whole document produces roughly the average of everything in it. That is fine when a document is about one thing. Enterprise documents are rarely about one thing.

Picture a customer file holding identity details, two years of transactions, a prior alert and a complaint. One vector for that file sits at the centre of all four topics, and is a close match for none of them. Ask about the complaint and the file is a weak match, because three quarters of its representation is about something else.

We measured it. Growing documents from one topic to ten, holding corpus, encoder and scoring fixed, <Term k="ndcg">nDCG@10</Term> fell from **0.815 to 0.294**. Giving each document several vectors instead of one recovered it to **0.803**. Same corpus, same encoder, only the representation changed.

The mechanism behaves as theory predicts. The similarity between a question and its target document's best individual piece stayed flat as topics accumulated, 0.476 to 0.466, while the pooled vector's similarity decayed from 0.476 to 0.225. The signal was never lost. It was averaged away.

## The correction that matters more than the finding

<TeachingIllustration src="/images/ladder/context-aspect-dilution-labeled-v2.webp" alt="One customer dossier becomes a blurry blended representation in one path and four distinct topic representations in another." title="One blended vector hides the part you asked for" caption="Identity, transactions, alerts and correspondence pull a pooled representation in different directions. Keeping several searchable units preserves the signal that averaging would weaken." />

Splitting a document into several pieces gives it more vectors, and more vectors means more chances to match. So the honest question is not "do several vectors beat one" but "do purpose-shaped pieces beat the same number of arbitrary pieces".

We ran that control, and on real prose our clever version lost: purpose-shaped cards scored 0.635 against plain chunking's 0.667. We published it. The lesson is the method rather than the result. Anything you adopt here has to beat a <Term k="matched control">matched control</Term> at equal capacity on your own queries, or you have measured the extra capacity and called it insight.

## Keyword search is not optional

Meaning-based search is poor at exact strings. On queries naming a specific attribute, keyword search scored **0.997 against 0.314** for the dense index on identical queries. Running both and fusing the rankings costs almost nothing and removes a silent failure: a dense-only system does not return an error when it misses an account number, it returns something plausible instead.

## Memory is context that lasts

**In short:** What an agent keeps from earlier work reaches the model like any document. It also carries duties a document does not.

The guide grades memory by how long it lasts. The current conversation and the evidence fetched for this turn are engineering. So is a working session of hours or days, within limits on where it is held and for how long. Memory that outlives the session is different. A durable profile of a customer or a case is a record, with an owner, consent, retention and deletion duties.

Four rules follow, and each rests on published evidence.

**Keep the source text.** Store the original and add search keys to it. On a published long-term memory benchmark, keeping raw text and adding derived keys improved recall by 9.4 percent and answers by 5.4 percent. Replacing the text with extracted facts or summaries made results worse (LongMemEval, ICLR 2025).

**Record when a fact was true.** Keep the time something happened apart from the time it was stored. A fact that has been replaced is then marked out of date, and the history behind an earlier decision survives. Stale grounding is a named production failure.

**Check a memory before it is kept.** Every write carries its source and waits in quarantine until it is promoted. The reason is measured: poisoning under 0.1 percent of a memory store achieved over 80 percent attack success (AgentPoison, NeurIPS 2024).

**Topics help search. They are not memory.** Topics are labels, stored so they can be rebuilt. A graph is added only where questions follow exact relationships, such as ownership or dependency. [CD-1](/decisions#cd-1) records that verdict.

## At the bank

The financial crime agent needs the customer's history. That history is exactly the aspect-rich material above: onboarding and identity, expected activity from the customer's stated business, two years of transactions, prior alerts and their dispositions, correspondence, and any prior report filed.

**One vector per customer file does not work**, for the reason set out above. Each part gets its own representation, and the question decides which is searched.

**Keyword search is doing heavy lifting here**, more than in most domains. Investigations turn on exact strings: account numbers, sort codes, counterparty names, reference fields, sanctions list entries. A near-match on a name is not a match, and getting it wrong in either direction is expensive.

**Permission filtering happens before the search, not after.** The index carries the access rights of each source, and retrieval is filtered on the analyst's live identity before ranking. Filtering afterwards leaks information: result counts alone tell you something exists that you may not see. In a bank this is not a refinement, it is the difference between a compliant system and a reportable incident.

**More is not better.** Adding documents can reduce accuracy until the corpus is scoped: published work shows accuracy falling below 40 percent until domain-scoped curation fixed it (arXiv 2606.11350). The agent that retrieves fifty documents per alert is usually worse than the one that retrieves eight good ones.

**What the agent remembers is a record.** Notes the agent keeps from earlier alerts on the same customer are durable memory about that customer. They carry their source and date. They wait for review before a later alert relies on them. An erasure request for the customer reaches them too, like every other copy.

**Someone owns the corpus.** Curation labour can be human, automated with sampled audits, or both, but accountability cannot be automated away. In *Moffatt v. Air Canada* (BC Civil Resolution Tribunal, 14 February 2024) the company was liable for its chatbot's statements where they contradicted its actual policy.

## The test for moving on

**Your representation beats a matched control on your own queries, anything the agent keeps is sourced, dated and checked, and what still fails is about acting rather than knowing.**

An agent that retrieves the right documents and then draws the wrong conclusion, calls the wrong tool, or stops too early does not have a context problem. That is [step 3](/ladder/tools-and-the-loop).
