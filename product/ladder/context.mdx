<Slide journey="ladder/context" id="cx-01">

Step two is about what an AI model gets to see. Everything the model can see when it answers is called its context. To get there, documents are cut up, turned into numbers, stored and searched. In our own measurements, these choices changed the answer more than anything else.

</Slide>

<Slide journey="ladder/context" id="cx-intro">

Some changes to an AI system are worth trying before others. The first three are tried in order, one step at a time. This order is called the ladder. Step one was the instructions you give the model. This is step two, context.

First, we follow a document on its way to the model. Then we see what goes wrong when one document covers many topics. We also see how to test a fix fairly. After that, we look at searching for exact details.

Then we look at who chooses and owns the documents. Last, we look at what is kept for later use. The video ends with the test for moving on.

</Slide>

## How a document reaches the model

<Slide journey="ladder/context" id="cx-02">

A system that uses a model to do a job is called an agent. To answer questions, an agent often needs facts from documents. Let us follow one document on its way to the model.

First, the file is read and turned into text. Then the text is cut into smaller pieces.

Each piece is turned into a list of numbers. The numbers are stored so they can be searched quickly.

Then a question comes in. The best pieces are found and passed to the model. Each stage has its own name. We will take them one at a time.

</Slide>

<Slide journey="ladder/context" id="cx-20">

The first stage turns the file into plain text. This is called parsing. Good parsing keeps the structure, like the rows and columns of a table.

Say a table is flattened into one long sentence. The numbers lose the labels that went with them. No later stage can put that back. So keep checking samples of the parsing.

</Slide>

<Slide journey="ladder/context" id="cx-21">

The second stage cuts the text into pieces that search can find. These pieces are called chunks.

A chunk that is too large mixes several topics. A chunk that is too small loses the text around it. Without that text, it can lose its meaning.

No single size works for every set of documents. So the size has to be tested.

</Slide>

<Slide journey="ladder/context" id="cx-22">

The third stage turns each piece into a list of numbers. The numbers stand for what the piece means. This list of numbers is called a vector.

Think of each vector as a point on a map of meaning. Pieces that mean similar things sit close together. Pieces about different things sit far apart.

</Slide>

<Slide journey="ladder/context" id="cx-23">

The fourth stage stores the vectors so they can be searched fast. This store is called an index.

The index also records who is allowed to see each document. The search uses that record later.

</Slide>

<Slide journey="ladder/context" id="cx-24">

The last stage starts when someone asks a question. The question is turned into a vector in the same way. The search finds the pieces whose vectors sit nearest to it.

Those pieces are passed to the model along with the question. Finding and passing on the right pieces is called retrieval.

</Slide>

<Slide journey="ladder/context" id="cx-13">

Retrieval needs one more rule. Not everyone is allowed to see every document. One way is to search everything first. Then remove what the person may not see. The other way narrows the search first. It only searches what that person is allowed to see.

Filtering afterwards leaks information. Even the number of results can show that a hidden document exists. Filtering first gives no such hint.

</Slide>

## The failure that catches almost everyone

<Slide journey="ladder/context" id="cx-04">

Now to a mistake that catches almost everyone. Say a whole document gets just one vector. That vector is roughly the average of everything in the document. That is fine if the document is about one thing. But documents at work are rarely about one thing.

Picture a long document that covers four different topics. Its one vector sits in the middle of all four. It is close to none of them.

Now ask about just one of those topics. The document comes back as only a weak match.

</Slide>

<Slide journey="ladder/context" id="cx-05">

We tested this in our own experiments. We made each document cover more topics, from one up to ten. Everything else stayed the same. Search quality fell sharply.

Then we gave each document several vectors instead of one. That brought search quality almost all the way back. We repeated this on two different machines. The result was the same.

</Slide>

## Make the test fair

<Slide journey="ladder/context" id="cx-06">

There was a problem with that result. Several vectors give a document more chances to match a question. So some of the gain might come just from having more pieces.

We ran a fairer test to check. We shaped pieces around what each part of a document was for. We compared them with the same number of plain chunks. On real text, our shaped pieces did worse.

</Slide>

<Slide journey="ladder/context" id="cx-07">

So test any new design against a plain version. Give the plain version the same number of pieces. A fair comparison like this one is called a matched control.

Your design has to beat it on your own questions. Otherwise you are only measuring the extra pieces.

</Slide>

## Keyword search is not optional

<Slide journey="ladder/context" id="cx-08">

So far, search has worked by meaning, using vectors. Search by meaning is poor at exact details, like a phone number. Another kind of search looks for the exact text. This is called keyword search.

In our tests on exact details, keyword search scored far higher. Search by meaning does not show an error when it misses. It returns something that looks right instead.

So run both kinds of search and merge the results. It costs almost nothing.

</Slide>

## Looking after the documents

<Slide journey="ladder/context" id="cx-14">

Now think about which documents belong in the search at all. The whole set of documents that can be searched is called the corpus.

Adding more documents can make answers less accurate. Published work showed accuracy coming back once the corpus was narrowed to the subject. A few good documents usually work better than many.

</Slide>

<Slide journey="ladder/context" id="cx-16">

Someone has to choose and tidy the documents in the corpus. This can be done by people, by software with spot checks, or by both. But one person or team must still own the corpus.

A real legal case shows why. In Moffatt versus Air Canada, the company's chatbot went against its own policy. The company was held responsible for what the chatbot said.

</Slide>

## Memory is context that lasts

<Slide journey="ladder/context" id="cx-25">

Documents are not the only thing the model sees. An agent can also keep notes from its earlier work. What it keeps is called memory.

When memory is used, it reaches the model just like a document. So it needs the same care as a document. It also brings some extra duties.

</Slide>

<Slide journey="ladder/context" id="cx-09">

Memory can last for different lengths of time. Some lasts only for the current conversation.

Some lasts for a stretch of work of hours or days. Both of these are ordinary engineering choices.

Memory kept after the work ends is different. It becomes a record. It needs someone who owns it. It also needs consent to keep it. And it needs rules for how long it is kept and when it is deleted.

</Slide>

<Slide journey="ladder/context" id="cx-10">

Four rules follow from published evidence. First, keep the original text. Then add labels to help search find it. In published tests, swapping the text for short facts or summaries made results worse.

Second, record when something happened. Keep that apart from the time it was saved. Then a fact that has been replaced can be marked out of date.

Third, check every new memory before it is kept. It carries its source and waits for review. In published work, planting bad entries in a tiny part of a memory store made most attacks succeed.

Fourth, topics are only labels that help search. They are not the memory itself. They can be rebuilt from the kept text.

</Slide>

## The test for moving on

<Slide journey="ladder/context" id="cx-17">

So when is step two done? There are three signs. First, your way of splitting and storing documents beats a matched control. It has to win on your own questions.

Second, everything the agent keeps has a source and a date. It has also passed a check.

Third, the agent now finds the right facts. What still goes wrong is what it does with them.

</Slide>

<Slide journey="ladder/context" id="cx-18">

Here is what that looks like. The agent finds the right documents. Then it draws the wrong conclusion, takes the wrong action, or stops too early.

That is not a context problem. It belongs to [step three](/ladder/tools-and-the-loop), tools and the loop.

</Slide>

## What to remember

<Slide journey="ladder/context" id="cx-recap">

Here is what to remember from step two. A document is parsed, cut into chunks, turned into vectors, indexed and retrieved. One vector for a document about many topics matches each topic only weakly. Test any new design against a matched control on your own questions.

Run keyword search alongside search by meaning. Give everything the agent keeps a source, a date and a check. Next is step three, tools and the loop.

</Slide>
