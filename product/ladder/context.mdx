An agent misses a document you know is in the store. **Why does the model not see the evidence it needs?** Often the cause is how the documents were prepared for search. Documents are cut into pieces, turned into numbers, stored and searched. Each of those choices changes the answer. On our own measurements, they change it more than anything else available. The most common failure is simple. A document about several things gets one averaged summary, so a question about one of them matches it weakly. This is the second step on [the intelligence ladder](/ladder).

## The pipeline, in order

**Parse.** Turn the source file into text and keep its structure. A table that becomes a run-on sentence has lost the link between each figure and its label. No later stage recovers it. Parsing quality sets the ceiling for every later stage. So it is spot-checked for as long as the system runs, never assumed.

**Chunk.** Split the text into pieces that can be retrieved. Too large, and one piece covers several topics. Too small, and a piece loses the context that gave it meaning. No single recipe works across every collection of documents. So the split is tested, not just configured.

**Embed.** Turn each piece into a vector, also called an <Term k="embedding">embedding</Term>. A vector is a list of numbers. It places the piece in a space where nearby means similar in meaning. Every vector records the version of the model that produced it. Changing that model invalidates the whole index.

**Index.** Store the vectors for fast nearest-neighbour search. Store the source's access rights alongside them. Indexes that respect who may see what belong to [the data platform layer (R02)](/layers/r02-data-platform).

**Retrieve.** Turn the question into a vector the same way. Find the nearest pieces and pass them to the model.

## One vector per document averages away the topic

Embedding a whole document gives roughly the average of everything in it. That is fine when a document is about one thing. Company documents are rarely about one thing.

Picture a customer file holding identity details, two years of transactions, a prior alert and a complaint. One vector for that file sits at the centre of all four topics. It is a close match for none of them. Ask about the complaint, and the file matches weakly. Three quarters of its vector is about something else.

We measured it. We grew documents from one topic to ten, with the collection, the embedding model and the scoring held fixed. Search quality fell from **0.815 to 0.294**. The score used is <Term k="ndcg">nDCG@10</Term>. It rates the first ten results from 0 to 1. Giving each document several vectors instead of one brought it back to **0.803**. The documents and the model were the same. Only the representation changed.

The cause is what theory predicts. Take a question and the best single piece of its target document. Their similarity stayed flat as topics were added, from 0.476 to 0.466. The whole-document vector, called a <Term k="pooled embedding">pooled vector</Term>, fell from 0.476 to 0.225. The signal was still there in the pieces. Averaging hid it.

## Test the fix against a fair control

<TeachingIllustration src="/images/ladder/context-aspect-dilution-labeled-v2.webp" alt="One customer dossier becomes a blurry blended representation in one path and four distinct topic representations in another." title="One blended vector hides the part you asked for" caption="Identity, transactions, alerts and correspondence pull a pooled representation in different directions. Keeping several searchable units preserves the signal that averaging would weaken." />

Splitting a document into several pieces gives it more vectors. More vectors means more chances to match. So the fair question is not whether several vectors beat one. It is whether pieces built around one purpose each beat the same number of plain pieces.

We ran that control. On real prose, the pieces built around one purpose each did worse. They scored 0.635 against 0.667 for plain chunks. We published that result. The method matters more than the result. Any design you adopt must beat a <Term k="matched control">matched control</Term> on your own queries. A matched control has the same number of pieces per document. Without it, you have measured the effect of more pieces, not of the design.

## Add keyword search

Meaning-based search is poor at exact strings, such as an account number. On queries naming a specific attribute, keyword search scored **0.997**. Meaning-based search scored **0.314** on the same queries. Run both and merge the two rankings. This is called <Term k="hybrid retrieval">hybrid retrieval</Term>. It costs almost nothing, and it removes a silent failure. A meaning-only system does not return an error when it misses an account number. It returns something plausible instead.

## What the agent remembers

What an agent keeps from earlier work reaches the model like any document. It also carries duties a document does not. Memory is graded here by how long it lasts.

The current conversation and the evidence fetched for this turn are working data. So is a working session of hours or days, within limits on where and how long it is held. Memory that outlives the session is different. A lasting profile of a customer or a case is a record. It has an owner, and duties for consent, retention and deletion. Governed memory is built in [the agent data engineering layer (R14)](/layers/r14-agent-data-engineering). [Knowledge and memory](/memory) covers it in depth.

Four rules follow, and each rests on published evidence.

**Keep the source text.** Store the original and add search keys to it. On a published long-term memory benchmark, this improved recall by 9.4 percent and answers by 5.4 percent. Replacing the text with extracted facts or summaries made results worse (LongMemEval, ICLR 2025).

**Record when a fact was true.** Keep the time something happened apart from the time it was stored. A fact that has been replaced is then marked out of date. The history behind an earlier decision survives. Acting on an out-of-date fact is a known production failure.

**Check a memory before it is kept.** Every write carries its source. It waits in quarantine, a holding area, until it is checked and promoted. The reason is measured. Planting false entries in under 0.1 percent of a memory store gave attacks over 80 percent success (AgentPoison, NeurIPS 2024).

**Topics help search. They are not memory.** Topics are labels, stored so they can be rebuilt. A graph is added only where questions follow exact relationships, such as ownership or dependency. [The decision on graphs and embedding search](/decisions#cd-1) records that verdict.

## Worked example: an audit investigation

<TeachingIllustration src="/figures/ladder/industrial-context.svg" mobileSrc="/figures/ladder/industrial-context-mobile.svg" title="Supply evidence for an audit investigation" alt="Four boxes in order. Question: which issue recurs? Sources: findings and action records. Context: site, dates and procedure. Answer: the supported pattern and the gaps." caption="Proposed industrial example. Evaluate against the simpler existing process before adopting it." />

An audit investigation at a utility or energy company needs the original finding and its site and date. It also needs the applicable procedure, the action history and the closure evidence. A set of similar sentences can suggest a topic. It can still miss the context needed to explain it.

Retrieve the relevant passages and records using the investigator's current permissions. Keep source identifiers and times. Compare plain chunks and keyword search before adding several representations per document. A graph or specialist embedding is useful only if it improves the actual questions.

A reviewer should be able to see why the evidence supports the proposed pattern. Missing evidence stays a gap. It must not become a confident conclusion about a systemic issue. See [systemic audit issues](/use-cases/systemic-audit-issues).

## When this step is done

**Your representation beats a matched control on your own queries. Anything the agent keeps is sourced, dated and checked. What still fails is about acting, not knowing.**

An agent may find the right documents and still draw the wrong conclusion. It may call the wrong tool or stop too early. That is not a context problem. It is [step 3](/ladder/tools-and-the-loop).
