A team wants an agent to do a job. Before anyone picks a model, one question comes first. **What must this agent understand, decide and do to finish the job well, and at what cost?** The answer is to change the cheap things first. Those are the instructions, the context, and the tools and loop around the model. Change the model itself only when a measured limit remains. The intelligence ladder is the order in which to try those changes. It belongs to [the build step](/start#5-build) on the Start page.

## Two pillars: intelligence and memory

An agent needs two things. **Intelligence** decides how it handles the task. **Memory** gives it information it can find, check and use as evidence. This page covers intelligence. [Knowledge and memory](/memory) covers the other pillar. Models and their training sit in [the intelligence and learning layer (R06)](/layers/r06-intelligence-and-learning), one of [the fourteen layers](/layers) of the estate.

## Match intelligence to the work

Using one capable model for every task makes trials easy. It does not show where reasoning adds value, or whether a complex agent pays for itself. Compare three kinds of work instead. These are choices to test, not a fixed order.

<TeachingIllustration src="/images/ladder/intelligence-budget-v1.webp" title="Match intelligence to the work and its full cost" alt="Three kinds of task. Known steps need rules or a fixed workflow, a small effort. Choosing the next check needs a bounded agent, a medium effort. Specialist judgement may justify testing a trained model, a larger effort with expert review. The cost elements are models, tools, data, review and errors. A testing gate compares the cost per successful task." caption="These are task choices, not maturity levels or measured cost rankings." expandable />

**Known steps.** Checking required fields before an inspection request goes in has known steps. Ordinary software or a fixed workflow may do it.

**Steps that depend on what is found.** Investigating an unexplained gap in production figures changes as it goes. The agent finds missing evidence, picks a tool, reads the result and decides what to check next.

**Specialist judgement.** Spotting a particular defect pattern needs expert judgement. Compare better inputs, specialist models and training. Train only when it fixes a demonstrated limit you can maintain.

A capable agent does not need broad authority. Set how freely it acts in [the autonomy contract](/architecture/autonomy-contract), apart from the model's capability.

## Change the cheap things first

Try the three changes that cost least first.

<Cards>
<Card title="Instructions: define good work" href="/ladder/instructions">Tell the agent the goal, the limits and the result you need. Otherwise its effort goes to the wrong task.</Card>
<Card title="Context: supply what matters now" href="/ladder/context">Give it the relevant evidence and the current state of the task. General knowledge cannot tell it the condition of one asset.</Card>
<Card title="Tools and the loop: investigate and act" href="/ladder/tools-and-the-loop">Let it fill a specific gap or perform an allowed operation. Then check what happened.</Card>
</Cards>

If those are enough, stop there. [The Agentic OS](/agentic-os) sets out the harness you build around the model and the runtime you buy.

## Count the full cost

Judge cost against the business outcome, not one model call. An investigation can involve many calls, tools, retries and expert review. A cheaper answer that creates rework can cost more in the end.

For a trial, add up the full cost of the evaluated cases, failed attempts included. Add supervision time at the full hourly cost of the people doing it. Add the cost of fixing wrong outcomes. Divide the total by the outcomes accepted as resolved to the agreed standard. That is the <Term k="cost per resolved outcome">cost per resolved outcome</Term>. Report failures and serious errors separately, so a good average cannot hide them.

Compare designs on the same cases. For example, test a rules-based workflow, a smaller model with retrieval, and a stronger model allowed to investigate. Route hard cases to a stronger model only if you can reliably spot them. Spread build and upkeep costs over realistic volumes. Each agent has a budget with hard caps, tracked in [the observability and FinOps layer (R12)](/layers/r12-observability-and-finops). [Value and full cost](/use-cases/value-and-investment) builds the business case.

## Change the model only when a measured limit remains

When the cheap changes stop helping, five options change the model itself. They can be combined. Use only the ones the failure calls for.

<Cards>
<Card title="Adapters and fine-tuning" href="/ladder/adapters-and-fine-tuning">Teach a repeatable behaviour from examples when the current behaviour is the limit.</Card>
<Card title="Distillation" href="/ladder/distillation">Test whether a proven capability can run on a smaller model at acceptable quality.</Card>
<Card title="Reinforcement fine-tuning" href="/ladder/reinforcement-fine-tuning">Use feedback on outcomes where the quality of a decision can be graded reliably.</Card>
<Card title="Continued pretraining" href="/ladder/continued-pretraining">Train on your own raw text when the evidence supports that investment.</Card>
<Card title="Custom pretraining" href="/ladder/custom-pretraining">Consider a specialist model when the task and data justify its full development cost.</Card>
</Cards>

Any model change re-runs the evals and the risk check at the change stage of [the agent lifecycle](/architecture/agent-lifecycle). [The learning flywheel](/architecture/learning-flywheel) sets out how it is tested and promoted.
