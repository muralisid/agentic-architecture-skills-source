<Slide journey="ladder/custom-pretraining" id="ca-01">

At the top of the market, two very different things are sold in similar words. This chapter helps you tell which one is in front of you.

</Slide>

<Slide journey="ladder/custom-pretraining" id="ca-intro">

This is the last chapter of the ladder. It is one of five ways to change the model itself. Very few organisations ever need it.

First, we look at two offers that sound alike. Then we look at path one. That is building your own model from nothing.

Next is path two. It is a different kind of model for data that is not text. Last, we see how this links back to the rest of the ladder.

</Slide>

<Slide journey="ladder/custom-pretraining" id="ca-20">

Start with how most AI models are made. They are trained on huge amounts of text from every subject. Then other models and products are built on top of them.

A large model like this is called a foundation model. Most teams start from one that someone else built.

</Slide>

<Slide journey="ladder/custom-pretraining" id="ca-02">

Here are the two offers. One is to build your own foundation model from nothing. The other is a different kind of model. It is built for data that is not text.

The first comes down to cost. It is almost never the answer. The second is real specialist work. It has a clear use.

</Slide>

## Path one: a foundation model of your own

<Slide journey="ladder/custom-pretraining" id="ca-03">

Start with path one. A model is a huge set of numbers. Training slowly adjusts those numbers. Here, the numbers start out random.

The model then reads trillions of small pieces of words. This huge first training is called pretraining. Nothing comes from an existing model. So everything it knows must come from your own text.

Last, it is tuned so that people can use it.

</Slide>

<Slide journey="ladder/custom-pretraining" id="ca-04">

Path one costs what only the biggest AI labs spend. It needs computing power costing tens of millions and more. It also needs a research team that stays in place.

Building takes a long time. The field keeps moving while you build.

Meanwhile, open and paid models keep getting better. Someone else pays for that.

</Slide>

<Slide journey="ladder/custom-pretraining" id="ca-05">

Path one does make sense in two cases. In the first, a national rule bans using any model from outside. This is called a sovereignty rule.

In the second, you hold a huge amount of text. It is so unlike public text that existing models get it wrong. This case also needs the money and the team.

</Slide>

<Slide journey="ladder/custom-pretraining" id="ca-06">

One question settles most plans to build your own model. What if you took an existing model and kept training it on your own text? That is called continued pretraining.

It gives most of what people want from their own model. It uses the same text. It costs a small fraction as much. And someone else keeps improving the model underneath.

</Slide>

<Slide journey="ladder/custom-pretraining" id="ca-07">

If you do take path one, one finding may help. It is about when to mix in text from your own field.

One study mixed a little of that text in from the very start. That beat training on public text first and adding your text later.

The study was published by a company that sells help with training data. It also used small models. It can guide how you run path one. It does not tell you whether to take it.

</Slide>

## Path two: when your data is not text

<Slide journey="ladder/custom-pretraining" id="ca-08">

Now for path two. The models on this ladder read text as a line of small word pieces. Some data is not like that at all.

Think of records linked to each other, or supply chains.

Think of streams of sensor readings, or molecules. None of this is a line of words. None of the earlier steps on this ladder can change that.

Much of this data is things joined by links. A set of things joined by links is called a graph.

</Slide>

<Slide journey="ladder/custom-pretraining" id="ca-21">

For data like this, the model itself has to be different. It has to learn from who is linked to whom.

The most common choice is called a graph neural network. In this chapter, we just call it a graph model.

</Slide>

<Slide journey="ladder/custom-pretraining" id="ca-22">

Here is how a graph model works, one step at a time. Take one thing in the graph, such as one record. It is called a node.

Each node starts with a list of numbers. The numbers describe that one thing.

</Slide>

<Slide journey="ladder/custom-pretraining" id="ca-09">

Now the model gets to work. It starts from each node's list of numbers.

A node's neighbours are the nodes it links to. Each node updates its numbers using its neighbours' numbers. One round of this is called a layer.

The model runs several layers, one after another. After two layers, a node knows about its neighbours' neighbours.

Last, the model reads each node's numbers to make a prediction. It learns from who connects to whom. A model that reads documents cannot see that.

</Slide>

<Slide journey="ladder/custom-pretraining" id="ca-10">

This way of working has two known problems. Each layer mixes a node's numbers with its neighbours' numbers. Stack enough layers, and nearby nodes end up with the same numbers.

Then the model can no longer tell them apart. This is called over-smoothing. It is why graph models in real use often have only two or three layers.

</Slide>

<Slide journey="ladder/custom-pretraining" id="ca-11">

The second problem pulls the other way. Information from a far node must pass through many nodes to arrive. The number of nodes on the way grows very fast with distance.

But each node holds only a fixed-size list of numbers. So far information gets squeezed through narrow links. Much of it is lost. This is called over-squashing.

</Slide>

<Slide journey="ladder/custom-pretraining" id="ca-12">

So the two problems pull against each other. More layers let information travel further. That eases over-squashing. But more layers make over-smoothing worse.

So turning one setting up does not fix both. People who have really done this work change the design of the model. A model's design is called its architecture.

Watch how someone handles this. It shows whether they have real experience.

</Slide>

<Slide journey="ladder/custom-pretraining" id="ca-13">

There are three more problems worth listening for. First, the learned numbers can stop being distinct. Or learning can fade out in the deeper layers. Then parts of the model quietly stop learning.

Second, a huge graph may not fit in memory. So it must be cut into parts. Every cut breaks real links. So the model trains on a graph with links missing.

Third, the training may be spread across many machines. Then training no longer behaves the way the textbooks describe.

</Slide>

<Slide journey="ladder/custom-pretraining" id="ca-14">

So when does path two make sense? It fits when what you predict depends on how things link together. It does not sit inside any one document.

The data must also be big enough for these problems to really matter.

This situation is easy to spot. The rest of this ladder is about AI systems that carry out tasks. These systems are called agents. Path two has little to do with them.

</Slide>

## How this connects back

<Slide journey="ladder/custom-pretraining" id="ca-16">

Now, how does this connect back to agents? The graph model is not the agent. It does not chat. It runs on its own as a scoring system. That system has its own checks on whether the model can be trusted.

The agent reaches the score by asking a small program to fetch it. A program like this is called a tool. It returns the score and the part of the graph behind it.

The agent uses them as evidence in its draft. A person makes the decision.

</Slide>

<Slide journey="ladder/custom-pretraining" id="ca-17">

This also means two different teams. Every earlier step on this ladder starts from a model that already exists. An engineering team builds around it.

The graph model needs a research team that builds models. That team has its own way of checking and approving models.

These are two different kinds of work. They meet at the tool. Giving the graph model to the agent team is a mistake. So is giving the agent to the graph team.

</Slide>

<Slide journey="ladder/custom-pretraining" id="ca-18">

Before building a custom graph model, try the simpler options. First, work out a few simple measures of the graph by hand. Then feed them to a simple model.

Second, try a ready-made graph model. Keep it only a few layers deep.

Third, try rules for patterns you already know. Each of these options gets a fair run first.

</Slide>

<Slide journey="ladder/custom-pretraining" id="ca-23">

Then compare them fairly. Use past cases where you already know the right answer. These are called labelled cases.

The custom model must beat the simple options on your own labelled cases. This is the same fair test used at the start of this ladder.

</Slide>

<Slide journey="ladder/custom-pretraining" id="ca-19">

The same habit applies at every step of this ladder. Find out what is really failing before you spend money. Never assume a bigger version of what you have will fix it.

</Slide>

## What to remember

<Slide journey="ladder/custom-pretraining" id="ca-recap">

Here is what to remember. Building your own foundation model almost never pays. First ask what continued pretraining on the same text would give.

Data made of linked things may need a graph model. That model is a tool the agent calls. A different team builds it.

At every step, find out what is failing before you spend. The rule from the start of this ladder still holds. Change the system before you change the model.
