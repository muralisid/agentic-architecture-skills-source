<PlainTerms>
An agent is not one call to a model. It is a loop: the model asks for something, the system fetches it, the model reads the result and decides what to do next. Everything that governs that loop is the harness, and it is the part teams skip on the way from "the context is fine" to "we need to train a model". The evidence says it is usually the thing that was actually missing.
</PlainTerms>

## How the loop actually runs

The model is stateless. Every turn, the whole conversation is sent again, the model replies either with an answer or with a request to use a tool, and if it is a tool request your code executes it and appends the result. Repeat until the model answers or you stop it.

Three consequences follow, and they are the whole of harness design.

**The context grows every turn.** Each tool result is appended, so a long investigation fills the <Term k="context window">context window</Term> with old evidence. You must decide what to do about that, and the choice is not neutral. **Compaction** summarises the history, which is lossy and can quietly drop the detail the model needed. **Reset** starts fresh with a stated goal and a short handover, keeping durable state in files or a record rather than in the conversation. Reset is harder to build and generally more reliable, because a summary of a summary degrades while a written record does not.

**What outlives the run is memory.** A record kept only for the task is engineering. Once it is kept for later runs, it becomes memory. It then needs a named owner, carries its source, waits in quarantine before later runs trust it, and is reached by deletion. [Step 2](/ladder/context#memory-is-context-that-lasts) sets out those rules.

**Nothing stops the loop unless you stop it.** A model can call a tool that returns an unhelpful result, decide to try again, and do that indefinitely. Real harnesses cap iterations, cap wall-clock time, check for cancellation between turns, and expose a stop hook. These are not edge cases, they are the normal path.

**Tools are an interface you are designing.** A tool with a vague description gets called at the wrong times. A tool returning ten thousand tokens of JSON burns the context window that the reasoning needs. Tools are designed for a reader with no memory of your system, because that is what they have.

## Why the harness is not plumbing

Holding task, environment and model constant, harness choices measurably change the beliefs that drive an agent's later decisions, even where the final success rate looks the same (arXiv 2607.04528, July 2026). In retrieval-heavy work the harness choice can outweigh the retrieval architecture itself (arXiv 2605.15184, May 2026).

Two things follow. Published benchmark comparisons run across different harnesses are confounded, so a claim that model A beats model B may be a claim about the scaffolding. And your own agent's behaviour is a property of your loop, not only of the model you licensed.

A third finding is worth carrying: multi-agent failures are design failures rather than model failures. A taxonomy built from 150 traces and validated on more than 1,600 across seven frameworks identifies fourteen failure modes in three categories, and that is its central conclusion. A stronger model in a badly designed loop is still a badly designed loop.

## The multi-agent question, with the one published number

Splitting work across several agents buys parallel breadth and context isolation, at a cost multiplier of roughly 1.4 to 20 times. It does not buy reasoning quality per token.

On 10,000 SEC filings across 25 field types, five models and four coordination patterns, a hierarchical supervisor-worker design reached 0.921 F1 at 1.4 times the cost and was the best point on the cost-accuracy frontier. A reflexive self-correcting pattern reached 0.943 at 2.3 times. A hybrid captured 89 percent of the accuracy gain at 1.15 times (arXiv 2603.22651, March 2026).

The threshold that follows is the only published one: **multi-agent is justified when the accuracy requirement exceeds about 0.92 F1.** Below that you are paying a multiplier for something a single well-built loop delivers.

## In utilities and mining

A vegetation candidate arrives with a location and observation date. The agent checks the asset map, recent inspections, and existing work orders. If the image cannot establish the required detail, it prepares a field-inspection request rather than inferring exact clearance.

Each tool returns a bounded result with source references. The loop has a deadline, a cost limit, and a stopping rule. Permission checks remain outside the model. Creating a request is distinct from completing the inspection.

Begin with one agent or a fixed workflow. Add specialists only when they improve outcome quality or useful concurrency enough to justify coordination. See [vegetation inspection](/use-cases/vegetation-inspection).

## The test for moving on

**The loop is instrumented, failures are traced to a specific cause, and what remains is the model not knowing your domain.**

That word "traced" is the gate. If you cannot say which turn failed and why, you cannot know the model is at fault, and every option in Model adaptation costs more than finding out. For an inspection, a trace should show the sources consulted, tool responses, checks made, and the confirmed action.
