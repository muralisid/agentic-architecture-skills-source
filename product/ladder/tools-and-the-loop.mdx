This video is about what runs around an AI model. Often, that is where the real problem is.

</Slide>

<Slide journey="ladder/tools-and-the-loop" id="tl-intro">

This video covers Step 3 of the ladder: tools and the loop. Steps 1 and 2 worked on the instructions and on what the model reads. Step 3 works on the system that runs around the model. It is the last step before you change the model itself.

First, we look at how the loop runs and what it must handle. Then we see why it matters and when to split the work. Last comes the test for moving on.

</Slide>

## How the loop actually runs

<Slide journey="ladder/tools-and-the-loop" id="tl-21">

Let us start with how the loop works. Some AI systems do not answer a task in one go. The model asks for something. Your code fetches it and hands back the result.

The model reads the result and decides what to do next. This repeats until the model gives its answer. A system that works like this is called an agent.

</Slide>

<Slide journey="ladder/tools-and-the-loop" id="tl-22">

So how does the model get what it asks for? You give it a set of actions it may ask for. Looking something up is one example. When the model asks for one, your code carries it out. Each of these actions is called a tool.

</Slide>

<Slide journey="ladder/tools-and-the-loop" id="tl-03">

Let us follow one pass around the loop. One pass is called a turn. The model keeps no memory from one turn to the next. So every turn, the whole conversation is sent to it again.

The model replies with an answer or asks for a tool. If it asks for a tool, your code runs the tool. Then the result is added to the conversation.

This repeats until the model answers or you stop it.

</Slide>

<Slide journey="ladder/tools-and-the-loop" id="tl-25">

Something has to run all of this. It sends the conversation, runs the tools and adds the results. It also decides when the loop must stop. Everything that runs and controls the loop is called the harness.

</Slide>

<Slide journey="ladder/tools-and-the-loop" id="tl-02">

The harness is the part teams most often skip. They improve what the model reads. Then they jump straight to training the model. Training means changing the model itself. The evidence says the harness is usually what was missing.

</Slide>

## What the harness has to handle

<Slide journey="ladder/tools-and-the-loop" id="tl-27">

The harness has a few jobs to handle. The first one comes from the loop itself. Each turn adds another result to the conversation. So in a long task, the conversation keeps growing.

But a model can only read a limited amount of text at once. That limit is called the context window. A long task soon fills it with old results.

</Slide>

<Slide journey="ladder/tools-and-the-loop" id="tl-04">

When the context window fills up, the harness has to make room. There are two ways to do it.

The first way shortens the old conversation into a summary. This is called compaction. A summary can quietly drop the detail the model needed.

The second way is to start fresh. The harness keeps a written record of the task outside the conversation. Each fresh start begins from the goal and that record.

This is harder to build and generally more reliable. Each time the history is summarised again, a little more is lost. A written record does not lose detail this way.

</Slide>

<Slide journey="ladder/tools-and-the-loop" id="tl-05">

Usually that record is kept only for the task. Sometimes you keep it for later tasks too. A record kept like that is called memory.

Memory needs a named owner and a note of its source. It waits for a while before later tasks trust it. And there must be a way to delete it. Step 2 sets out these rules.

</Slide>

<Slide journey="ladder/tools-and-the-loop" id="tl-06">

The loop ends only when the model answers or you stop it. A model can get a poor result from a tool and try again. It can keep doing that forever.

So real harnesses set limits. They cap the number of turns and the running time. They check between turns whether the task was cancelled. And they give you a way to stop the loop.

Put a cap on the cost of each task too. Without it, one task that never ends can use up a whole day's budget.

</Slide>

## Tools and access

<Slide journey="ladder/tools-and-the-loop" id="tl-07">

The harness also runs the tools. So the tools themselves need care. The model has no memory of your system. A tool with a vague description gets called at the wrong times. So describe each tool for a reader who knows nothing about your system.

</Slide>

<Slide journey="ladder/tools-and-the-loop" id="tl-13">

What a tool sends back matters too. A huge block of raw data fills the space the model needs for thinking.

A raw data tool returns every row and every field it finds. The few rows that matter get buried. So the model reasons badly.

A better tool returns a short summary and flags what stands out. A second tool pulls the full detail on one of them. The model now has far less to read. It reasons better on the same data.

</Slide>

<Slide journey="ladder/tools-and-the-loop" id="tl-26">

Some people using an agent should not see everything it can reach. You might try to write a rule about this in the instructions.

But instructions and the content the model reads arrive in the same form. The model cannot reliably tell them apart. So a rule in the instructions cannot enforce access.

</Slide>

<Slide journey="ladder/tools-and-the-loop" id="tl-16">

So the check has to sit outside the model. The agent reaches other systems only through one checkpoint. This checkpoint is called a gateway.

On every request, it checks whether the person using the agent may see what was asked for.

</Slide>

## Why the harness matters

<Slide journey="ladder/tools-and-the-loop" id="tl-08">

So far we have seen what the harness does. But does it really change how an agent behaves? One study kept the task and the model the same. It changed only the harness.

The final success rate looked the same. But what the agent believed at later steps changed. So its later decisions changed too.

</Slide>

<Slide journey="ladder/tools-and-the-loop" id="tl-29">

This matters when you read that one model beats another. The two models may have run inside different harnesses. Then the result may say more about the harness than the model.

Your own agent is the same. How it behaves depends on your loop as well as your model.

</Slide>

## When to split the work across agents

<Slide journey="ladder/tools-and-the-loop" id="tl-30">

Up to now, we have looked at a single agent. Some designs split the work across several agents. Each agent runs its own loop on one part of the task. This is called a multi-agent design.

</Slide>

<Slide journey="ladder/tools-and-the-loop" id="tl-10">

More agents let parts of the work run at the same time. Each agent also has its own separate conversation. So no single conversation has to hold everything.

But they multiply the cost. And each agent reasons no better than a single agent would.

</Slide>

<Slide journey="ladder/tools-and-the-loop" id="tl-09">

One study looked at how multi-agent systems fail. It found the failures come from how the system is designed. They do not come from the model. So a stronger model does not fix a badly designed loop.

</Slide>

<Slide journey="ladder/tools-and-the-loop" id="tl-11">

So when is splitting the work worth the cost? One study tested several ways of coordinating agents. It used a large set of official company reports. It scored accuracy from zero to one.

Multi-agent is worth it when you need accuracy above about 0.92. Below that, one well-built loop does the job for less. This is the only published threshold.

</Slide>

## The test for moving on

<Slide journey="ladder/tools-and-the-loop" id="tl-18">

So when is this step done? There are three checks.

First, every turn of the loop is recorded and measured.

Second, each failure is tracked back to a specific cause.

Third, what still fails is the model not knowing your field.

</Slide>

<Slide journey="ladder/tools-and-the-loop" id="tl-20">

To track a failure, you need a record of each run. It shows which tools ran, what they returned and how many turns it took. This record is called a trace.

It also shows what the final answer claimed. And it shows the evidence behind each claim.

</Slide>

<Slide journey="ladder/tools-and-the-loop" id="tl-19">

This record is what tells you whether it is time to move on. If you cannot say which turn failed and why, you cannot know the model is at fault. Every change to the model itself costs more than finding out.

</Slide>

## What to remember

<Slide journey="ladder/tools-and-the-loop" id="tl-recap">

An agent is a model working in a loop. The harness runs that loop and sets its limits. Who may see what is checked at a gateway. Split the work across agents only when you need very high accuracy. Before changing the model, trace each failure to its cause.

The next step changes the model itself for the first time. Next up is adapters and fine-tuning.
