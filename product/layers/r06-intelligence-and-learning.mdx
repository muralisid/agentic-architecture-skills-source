The intelligence and learning layer (R06) is where an organisation builds, tests and improves its models. It is one of the [fourteen layers](/layers) you already own. Today it holds data science platforms and machine learning built into packaged products. It also holds image analytics bought as a service and a few general assistants. Agents change its job. An agent's behaviour can shift with every prompt edit, model upgrade or new rule. So this layer must provide evaluation and release, one of the [seven capabilities](/architecture/system-view) an agent platform adds. That means tests owned by experts and model graders checked against people. It also means a gate that every change passes before production, with a way back. The loop that runs all this is the [learning flywheel](/architecture/learning-flywheel). Improvement becomes a tested release, not something the agent does to itself.

## What agents add

<GuideFigure id="layer-06-hero" fullWidth />

Agents improve in three ways, at three speeds. The fastest is changing the <Term k="prompt">prompt</Term> and the context the agent sees. It is cheap, quick and easy to undo. The middle speed is changing what the agent retrieves and remembers. That work is governed, and the [agent data engineering layer (R14)](/layers/r14-agent-data-engineering) covers it. The slowest is changing the model's weights. That is rare, and it stays offline behind evaluation, safety review and rollback.

### Production and testing share one store

One choice decides whether improvement builds up over time. Production traces and test datasets should share one store. A <Term k="trace">trace</Term> is the step-by-step record of one agent run. When a live run scores badly, its trace becomes a new test automatically. Uber runs this loop. A person reviews each weak production case before it joins the test set. Databricks bought this capability with Quotient AI on 11 March 2026.

### Judges grade, people check the judges

Model <Term k="judge">judges</Term> grade outcomes at volume. A judge is a model that scores another model's work against a rubric. The rubric includes an explicit "Unknown" option. Judges grade outcomes, not the exact steps the agent took. People check a sample of the grades. Nothing grades its own work, so the process that proposes a change never scores it. Judges drift on hosted endpoints. So each judge is pinned to a version and checked against human labels as a standing job. The [observability and FinOps layer (R12)](/layers/r12-observability-and-finops) runs that check day to day.

### A rule earns its place

<TeachingIllustration src="/images/layers/r06-rule-promotion-labeled-v1.webp" title="A rule becomes policy only after it survives attempts to break it" alt="A real failure is labelled by experts and turned into a candidate rule. A counterexample search tries to break the rule. If a counterexample is found, the rule goes back for revision or rejection. A rule that survives then runs against the full test suite. It is promoted to policy outside the model. Beside the flow, a model judge is checked against humans and never grades its own work. The cycle is test, promote, monitor, demote." caption="Weak rules go back for revision. Promoted rules live outside the model, where they can be versioned, watched and removed." />

A rule learned from failures becomes policy only after it survives attempts to break it. Writing good rules is the hard part. In a July 2026 study, only 7 of 32 automatically learned policies were grounded and executable. Rules written by people did help. They lifted a frozen agent's success rate by 5.0 points. The study's own promotion gate failed in both directions. It accepted a rule that cut success from 5 in 20 to 1 in 20. It also rejected a rule worth 5 points.

So promote a rule on two tests. It must survive <Term k="counterexample">counterexamples</Term>, which are past cases that would break it. And the full test suite must not get worse. A method called AutoSpec runs this search automatically. It proposes a rule, looks for a trace that breaks it, and refines the rule until none does. It cut false positives by up to 94 percent. It settled within four to five rounds.

A promoted rule lands outside the model, as policy written in code. A rule the model only reads is still advice. The hard version runs at the tool gateway and the policy decision point. The [security and identity layer (R10)](/layers/r10-security-and-identity) owns that check. Every promoted rule also needs a way to be removed. Piled-up rules are not free. Instruction files written by a model cut success by about 0.5 to 3 points on two benchmarks. They also raised running cost by 20 to 23 percent.

### Only some rules can be fixed checks

A study of 2,116 statements in agent instruction files found that about a quarter can be enforced as written. Most depend on context that cannot be defined in advance. The rest stay judged behaviour, and judges can be attacked. On one benchmark, a class of attacks raised miss rates for 8 of 11 judges. So keep the set of fixed checks small, keep it outside the model, and size it to this limit.

### Guard the test rig

In April 2026, UC Berkeley researchers built an agent that could not solve any task. It still scored 100 percent on several public benchmarks, including SWE-bench Verified. On that benchmark, editing about ten lines in one test file passed every task. The leading flaw was that nothing kept the agent and the evaluator apart. So run the evaluator apart from the agent under test. Treat a benchmark score as a claim to check, not a measurement.

Watch what the score rewards. In an Anthropic study, models trained to game their reward behaved differently on other tasks. Alignment faking, meaning pretending to comply, appeared in 50 percent of probes. The business version is a proxy metric. Deflection counts conversations no person touched, including ones that ended with the problem unsolved. A healthier signal is the pass rate rising while the human revision rate stays flat or falls.

### Change the model last

Tune prompts and context first. GEPA, a prompt optimisation method shown at ICLR 2026, beat a reinforcement-learning baseline by 6 points on average. It used up to 35 times fewer trial runs. Next, distil to a smaller model when volume justifies it. <Term k="distillation">Distillation</Term> means teaching a small model to copy a large one. It pays off with a narrow workload, a locked test set and over about 50 million tokens a month. Use reinforcement <Term k="fine-tuning">fine-tuning</Term> only behind a grader that cannot be gamed.

What one agent learns at work stays in its own [memory](/memory) until it is tested. Learnings move from that memory into a tested release, never the other way.

### A worked example: billing exceptions

Take an energy retailer's billing exceptions. SAP already scores each implausible meter read with a release confidence [vendor]. A billing agent should start from that score, not from zero. Its test suite comes from specialists' past release decisions. The research for this guide found no such test sets in utilities yet. So the first job is to collect real cases and have two specialists agree on each verdict. After that, a weak live case becomes a new test once a person reviews it.

| Part | What it does | Where it runs |
|---|---|---|
| Test suite | Defines correct behaviour from real failures. Two experts must agree on each task | Versioned like code. Owned by domain experts |
| Judges | Grade outcomes at volume against a rubric with an "Unknown" option | Pinned model versions, kept apart from the optimiser |
| Human sample | Checks a sample of judge grades, and rare cases | Domain experts |
| Shared trace and test store | Holds production traces and test datasets together. Failing traces become tests | The [data platform layer (R02)](/layers/r02-data-platform) |
| Promotion pipeline | Takes candidate rules through counterexamples, the test suite and human approval. Removes them again | Offline, run like a software build pipeline |
| Policy-as-code rules | Run the promoted hard rules | The tool gateway and the policy decision point |
| Distillation pipeline | Builds smaller models where volume justifies it | Offline training infrastructure |

## What must be true before an agent touches it

Before any change to an agent's behaviour reaches production, these must hold.

- **Experts own the test bar.** Domain experts define correct behaviour, and engineers build the machinery. Start with 20 to 50 tasks drawn from real failures. Accept a task only if two experts would reach the same verdict.
- **Judges grade at volume, and people check them.** Expert review costs about 100 times as much as a model judge. So judges grade at volume, and people check a sample and the rare cases.
- **The evaluator is kept apart.** The test rig runs isolated from the agent under test. Judges are pinned and calibrated against human labels.
- **Promotion has a gate and a way back.** A rule needs counterexample survival, no test regression and human approval. Every promoted rule and model version can be rolled back.
- **The learning level is set.** The [autonomy contract](/architecture/autonomy-contract) sets how an agent may learn. The levels are fixed (L0), curated learning (L1), reviewed learning (L2) and continuous learning inside limits (L3).
- **A change re-runs the tests.** A new model, prompt, tool, permission, data source or memory policy is a change on the [agent lifecycle](/architecture/agent-lifecycle). Each one re-runs the evaluations and the [risk profile](/architecture/risk-profile) before release.
- **Traces are cleaned first.** Personal data is redacted before traces enter test datasets.

The enforcement point for this layer is the promotion gate in the release pipeline. For promoted rules, it is the policy decision point at the tool gateway. Both sit outside the model, as [enforcement outside the model](/architecture/enforcement) describes.

## Choices and their verdicts

Each choice is the common choice, tested against the simplest credible alternative. The full records are in the [decision catalog](/decisions).

- **[Fine-tuning versus prompt and context work](/decisions#cd-19) (CD-19):** do them in order. Tune context and prompts against a locked test suite, then distil, then fine-tune behind a hard grader.
- **Who owns the test bar:** domain experts, with engineering building the machinery. No credible published evidence puts agent quality with data science teams.

## Concerns this layer must honour

The ten cross-cutting concerns are set out in the [concern matrix](/architecture/concern-matrix). This layer carries a specific duty for six of them.

- **Traceability and audit:** every promoted rule keeps its evidence, meaning the counterexamples it survived and the test results it changed.
- **Grounding:** tests come from real failures, and benchmark scores are treated as claims to check.
- **Privacy:** personal data is redacted before traces enter datasets. Customer data in training needs consent.
- **Sovereignty:** a fine-tuned model inherits the erasure duties of the data it learned from.
- **Safety and oversight:** people approve each promotion, and reward gaming is watched.
- **Resilience:** every promoted change can be rolled back against the locked test suite.

## Evidence and limits

The main results are dated studies, not vulnerability records. They cover the policy pipeline study (July 2026), AutoSpec and the instruction-file analysis. They also cover an enforceability proof (July 2026), the reward-hacking study (November 2025) and the Berkeley benchmark report (April 2026).

Three figures come from vendors and carry the [vendor] tag. They are NVIDIA's cost claim, OpenAI's reinforcement fine-tuning gains and one fine-tuned versus prompted comparison. Gartner's figure on runtime enforcement failures by 2030 is a projection.

The policy study found no transfer beyond its own task family. The quarter-enforceable figure comes from instruction files, not from decisions in a live enterprise. No published measurement of the second exists. No published evidence shows which function should own agent quality at scale. This guide recommends domain experts, and the strongest published guidance agrees.
