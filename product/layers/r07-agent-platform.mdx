The agent platform layer (R07) is where agents run. It is one of the [fourteen layers](/layers) you own, and it is mostly new. Today it holds robotic process automation bots, workflow and rule engines, chatbots and copilots. Agent builders inside vendor products are arriving on top. When agents arrive, this layer becomes the home of the runtime. The runtime is one of the [seven capabilities](/architecture/system-view) an agent platform adds. This layer must provide a loop around the model with several independent ways to stop. It must keep each run's state where a person can read it, and survive a crash. It must also let only tested versions of an agent run. The loop around the model is called the <Term k="harness">harness</Term>. It decides what the model sees, what it may call and when it stops. Buy the runtime from a vendor. Build and own the harness yourself.

## What agents add

<GuideFigure id="layer-07-hero" fullWidth />

### The harness is the product

Everything that separates a working agent from a demo lives in the harness. It assembles and resets the context, calls tools, records state, checks the work and stops the loop. Production practice has settled on four habits. State lives outside the model's working memory, in files a person can read. Stopping rests on more than one condition. A separate agent or process checks the work, because models praise their own weak work. Recovery from failure is a planned path, not an afterthought.

Meta's production harness, called REA, has the strongest published results. It doubled average model accuracy across six production models [vendor]. Harness choice can also matter more than the retrieval method. On 116 memory questions run through four harnesses, plain text search generally beat vector search (May 2026). So a benchmark comparison across different harnesses cannot tell you which part made the difference.

### Every run has several ways to stop

A production loop needs several independent ways to stop. The limits are a step cap, a time cap and a cancellation check between rounds. They also include stop hooks, approval rules, a per-run token and cost budget, and a <Term k="kill switch">kill switch</Term>. Each agent has a budget with hard caps. The VS Code Copilot harness (May 2026) publishes its stop conditions. The Microsoft Agent Framework Harness (July 2026) gives the fullest published list of harness parts.

Tool approval is decided in the harness, because only the harness sees the whole loop. It is enforced at the tool gateway, because the harness is not a security boundary. The gateway sits in the [integration fabric layer (R03)](/layers/r03-integration-fabric).

### State lives in files a person can read

Long-running work keeps its state in three files [vendor]. The first is a feature list, with every feature marked failing at the start. The second is a progress log, and the third is the version history in git. Work runs one feature per session, with a fixed checklist at the start of each. Prefer resetting the context to squeezing it into a summary. Sub-agents return short summaries of 1,000 to 2,000 tokens, not full transcripts. Skills load their detail only when needed. Each skill costs about 100 tokens of always-loaded description. Its body, under 5,000 tokens, loads only when the skill is triggered [vendor].

### The run survives a crash

Saving a run's data is not the same as making the run survive. A checkpoint saves data, but a checkpointed run still lives in one process. If that process dies, the run dies with it [vendor]. <Term k="durable execution">Durable execution</Term> makes the run itself survive a crash. A pause for a human approval then uses no resources and survives worker restarts. That makes day-long approval waits affordable. Very long jobs can sleep and wake, as Meta's REA does. The other path avoids the engine entirely. Reset the context and carry state in the files above.

The [infrastructure and compute layer (R01)](/layers/r01-infrastructure) provides the durable sessions underneath. This layer decides which runs need them.

### Only tested versions run

<TeachingIllustration src="/images/layers/r07-lifecycle-labeled-v1.webp" title="A version earns and keeps its release status" alt="A version moves through five release states: draft, approved, published, deprecated and retired. Gates sit between them: offline evaluation, safety review, version and lineage checks, and a freshness check. A version that fails a gate is removed from circulation. A note reads: users can find only published agents. The line underneath reads: promotion is tested, demotion is automatic." caption="One published design for releasing a version. It sits inside the nine-stage agent lifecycle, which tracks the whole agent." />

One published design moves each agent version through five release states (Kang and Wang, July 2026). They are draft, approved, published, deprecated and retired. Each promotion gate has a named threshold. For example, correctness must be at least 0.90 and harm at most 5 percent. Each agent is re-tested every 7 days and demoted if it fails. Search through MCP returns only published agents, so a weaker agent becomes harder to reach. This is a six-agent proof of concept by a cloud consultancy, not observed enterprise practice.

These five states track one version's release inside the nine-stage [agent lifecycle](/architecture/agent-lifecycle), which tracks the whole agent. Draft and approved fall in its evaluate and approve stages, and published means the registry state active.

An agent's autonomy level is itself a versioned setting that needs review to change. Prompt refinements take a light review. Model updates and autonomy changes take a full review. The levels are set out on the [autonomy contract](/architecture/autonomy-contract) page. One pharmaceutical programme publishes five levels of agency. It requires policy enforcement at the AI gateway before the higher levels are switched on.

### Simple routing beats clever routing

A May 2026 study by Rice and Amazon compared 21 routing methods across 5 benchmarks. The top 5 finished within 0.22 points of each other. All of them trailed a perfect router by 10 to 30 points. Hard queries caused most of that gap. A simple nearest-neighbour lookup beat the trained methods on every benchmark. So a cleverer router does not help much. What helps is fixed first-step rules, clear limits on which model handles what, and fallbacks. About 70 percent of instrumented organisations run three or more models [vendor]. Light models handle extraction and tagging, and large models handle synthesis.

### What moves between vendors

Managed runtimes now accept most agent frameworks. One hyperscaler runtime takes LangChain, the OpenAI Agents SDK, the Claude Agent SDK, Strands or your own code. Harnesses stayed custom. So the runtime is now easier to move between vendors than the harness. Prompts, tool definitions, model choice and Agent Skills move between vendors. Control flow, saved state formats, human-pause handling and approval models do not. Put portability effort into the harness design, not into the choice of framework.

### A worked example: alarm investigation

AWS published a reference design for utility alarm investigation on its agent runtime (September 2026) [vendor]. One agent reads work orders from Maximo, and another reads the PI historian. Both have read-only database access. The utility behind it is not named. In this shape, the runtime is bought and the harness decides what each agent reads and when it stops. Any work order the investigation proposes should stay a draft until a person approves it.

| Part | What it does | Where it runs |
|---|---|---|
| Harness | Assembles and resets context, runs the tool loop, stops and recovers. Holds the caps, budgets, approval rules and kill switch | Built in-house, deployed on the managed runtime |
| Managed runtime | Sandbox, session store, identity, scaling and crash survival | A hyperscaler agent runtime or a self-hosted equivalent |
| Checking path | Grades outputs apart from generation | A separate evaluator agent or process |
| Agent registry | Holds each agent's lifecycle state and each version's release state | Beside the tool catalogue in the integration fabric layer (R03) |
| Skill library | Curated skills, signed and version-pinned | An internal repository |
| Model router | Sends each request to the right model, with fixed first-step rules and fallbacks | The model gateway you already run |
| Durable execution engine | Keeps runs alive through crashes and long approval pauses | A workflow engine, or state files instead |

## What must be true before an agent touches it

Before an agent runs on this platform, these must hold.

- **It is registered.** A registry record holds its lifecycle state, its owner and its sponsor.
- **It has its own identity.** The [security and identity layer (R10)](/layers/r10-security-and-identity) issues it. The harness carries the caller's identity into every tool call. The [delegation chain](/architecture/delegation-chain) then traces each action to the person who asked.
- **It has several ways to stop.** Step and time caps, a cancellation check and stop hooks are set. Approval rules, a capped budget and a kill switch are set too.
- **Checking is separate.** The part that generates the work never grades it.
- **State is readable.** Long-running work keeps its state outside the context, in files a person can inspect.
- **Crash recovery is tested.** Runs that wait on people use durable execution or carry their state in files.
- **Its autonomy is set and versioned.** Changing it needs a full review.
- **Its skills are signed.** Skills and instruction files are version-pinned and checked for scope before use.

The harness is not the enforcement point. It decides when to ask for approval. The tool gateway and the policy decision point enforce the answer, outside the model. That is [enforcement outside the model](/architecture/enforcement).

## Choices and their verdicts

Each choice is the common choice, tested against the simplest credible alternative. The full records are in the [decision catalog](/decisions).

- **[One agent or many](/decisions#cd-21) (CD-21):** use several agents only for wide work that splits into independent parts. Most famous multi-agent gains came from spending about 15 times the tokens.
- **[Vendor-embedded agents or your own](/decisions#cd-17) (CD-17):** use the vendor's agent when work stays inside one product. Use your own agents when work spans systems.
- **[Replace robotic process automation or keep it](/decisions#cd-3) (CD-3):** keep the bots running beside agents, under supervision. Replace one only when a workload earns it.
- **Build or buy the harness:** buy the runtime, build the harness, and expect to own its upkeep. No credible published dataset exists for this choice.

## Concerns this layer must honour

The ten cross-cutting concerns are set out in the [concern matrix](/architecture/concern-matrix). This layer carries a specific duty for seven of them.

- **Identity and access:** the harness carries caller identity into every tool call. Approval rules live in the harness and are enforced at the gateway.
- **Observability:** loop telemetry covers steps, stops by type, context resets and how many sub-agents ran.
- **Traceability and audit:** session files and event logs are the durable record. Each released version traces to its test evidence.
- **Grounding:** checking is separate from generation. Self-assessment is distrusted by default.
- **Safety and oversight:** caps, stop hooks, approval rules and the kill switch.
- **Cost:** per-run budgets are enforced in the harness. The multi-agent token cost is chosen per task.
- **Resilience:** durable execution or state in files, with crash recovery tested.

## Evidence and limits

The failure record here comes from traces, not vulnerability records. A taxonomy called MAST (NeurIPS 2025) was built from 150 traces and checked on more than 1,600. It names 14 failure modes and finds that multi-agent failures are design failures. A benchmark contest over 2,196 traces found that spending more tokens did not predict success. Winning teams improved their guardrails, not their architectures.

Several figures come from vendors and carry the [vendor] tag. They include the multi-agent token figures, the three-file pattern and the checkpoint framing. The framework and single-call telemetry also comes from vendors, though it was measured, not self-reported. The five-state release design is a six-agent proof of concept.

This guide recommends judging an embedded agent by tested behaviour and logged exceptions, not by its autonomy. Every published taxonomy reviewed uses autonomy or action scope as its defining test. By that test, a deliberately bounded advisory agent would not count as an agent at all.
