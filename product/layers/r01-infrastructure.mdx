The infrastructure and compute layer (R01) is the servers, networks and cloud accounts that every system runs on. It is the base of the [fourteen layers](/layers). Today it holds data centres, public cloud, and a plant network kept apart from the office network. For agents it must provide five things. Each agent session runs in its own sealed workspace. Its only way out is a guarded exit to named destinations. Each agent holds its own identity, never a person's login. Sessions survive a crash and sleep while they wait. Model capacity is rented by default, and data sensitivity decides where a model runs.

## What agents add

Three kinds of infrastructure are new with agents: sandboxes, durable sessions, and a controlled exit to the network. None of them existed in the estate before agents. Together with model serving, they make up the runtime, one of [the seven capabilities an agent platform provides](/architecture/system-view).

### A sealed workspace for each session

Every agent session is isolated from every other session. An agent that can act needs a sandbox: a sealed workspace where its code, browsing or computer use runs. Agents that only chat and look things up do not need one. They still need the exit controls below.

For untrusted code that touches sensitive data, the sandbox is a micro virtual machine (microVM) or a Hyper-V boundary. A microVM is a small virtual computer with its own operating system kernel, such as Firecracker or Kata. gVisor runs a kernel in ordinary user space, so it is a middle level of isolation. Run it with non-default features off and patch it promptly. A plain container is never the boundary. In a 2026 benchmark, frontier models escaped misconfigured containers about half the time. The three largest cloud providers and the two major AI labs now isolate agent sessions this way [vendor]. The cost is start time: containers start in under 90 milliseconds, microVMs in seconds [vendor].

Choose the isolation level by what the agent can do, not by the product's name. Its permissions are what its own credentials let it do. The test is under what must be true, below.

### One guarded exit to the network

All traffic out of a sandbox passes through an egress proxy. Egress means traffic leaving the workspace. The proxy allows named destinations only, and there is no other route out. Allowing a domain allows everything that domain can do. So the strongest allowlists name operations, such as "upload only to our own tenant". Egress control matters even for agents with no sandbox. EchoLeak, a 2025 attack on Microsoft 365 Copilot, stole data with no user action. No compute control would have stopped it. Egress and output controls are the ones that answer it.

### An identity for each agent

Each agent gets its own identity, the machine version of an ID badge. This guide calls that minimum the agent's own identity (ID2). Shared credentials (ID1), where an agent uses a person's login, are the pattern to remove. Three kinds of agent identity ship today. One is a directory account, such as Microsoft Entra Agent ID [vendor]. One is the IETF's WIMSE standard with SPIFFE, run in production at Block. One is Okta's Cross App Access, now part of the MCP standard. This layer issues the identity. The [integration fabric (R03)](/layers/r03-integration-fabric) checks it on every tool call. [Security and identity (R10)](/layers/r10-security-and-identity) sets the rules for it. The [delegation chain](/architecture/delegation-chain) traces every action back to the person who asked.

### Sessions that survive a crash

Agents run for minutes or hours, and they get interrupted. The runtime keeps an event log of each step, so a session resumes after a crash. It can also snapshot a session and restore it, which is the undo after a bad action. Idle sessions sleep and cost nothing while they wait [vendor]. That matters, because agents spend 30 to 70 percent of their time waiting on models and tools. How the agent's own work is checkpointed is a choice for the [agent platform (R07)](/layers/r07-agent-platform). This layer supplies the event log, the snapshots and the sleep.

### Where models run

Rent model access by default and pay per use. Running your own models pays only above roughly 100 to 250 million tokens a month, per workload. Tokens are the small units of text a model reads and bills by. The volume must be sustained, and the hardware must be busy 60 percent of the time or more. At 10 percent use, the cost per token rises about tenfold. These figures are ranges from four practitioner analyses, none peer reviewed.

Open-weight models publish their trained weights, so anyone can run them. Many services sell them per use at low prices. So the cheap path is an open-weight model through a metered service, not your own hardware.

Data sensitivity decides where a model runs. Most work goes to a metered service. Restricted data goes to a sovereign region, a cloud region run under local law. The most sensitive data goes to air-gapped or self-hosted serving, cut off from outside networks. Do not assume the newest chips will get cheaper. Reserved prices for one common chip rose about 40 percent between October 2025 and March 2026.

### The parts and where they run

| Part | What it does | Where it runs |
|---|---|---|
| Agent runtime | Runs each session apart from the others, with budget caps and a kill switch | A cloud provider's agent runtime, or an edge platform |
| Sandbox | Runs code, browsing and computer use in a sealed, short-lived workspace | Per session, started by the runtime |
| Egress proxy | The only network path out, with allowlists and logs | The network edge of the runtime |
| Identity provider | Issues and proves each agent's identity | Your directory, a workload identity service, or your identity provider |
| Session store | Keeps the event log, snapshots and sleeping sessions | Built into the runtime, or a durable execution engine |
| Model serving | Delivers model calls at the right sensitivity level | Metered service by default, then a sovereign region, then air-gapped or self-hosted |

## What must be true before an agent touches it

**The sandbox matches what the agent can do.** Use Meta's Rule of Two. Does the agent hold private data? Does it read untrusted content? Can it send data out or change things? An agent with all three needs the strongest isolation. A new tool grant changes its permissions, so the [risk profile](/architecture/risk-profile) is scored again. Agents gather tools over time, so check on every grant, not only at launch.

**Everything a sandbox produces is untrusted.** Files, settings and tool configuration from the sandbox pass the same checks as content from the internet. They are checked before any host tool loads or runs them. There are no read-write mounts to the host. In 2026, agents wrote files that trusted host tools later ran [vendor].

**No credential inside a sandbox is worth stealing.** Tokens are tied to the session, short-lived, and useless outside the egress proxy. Local MCP servers read credentials from their environment by design. Register each one and limit what it can reach.

**The exit is locked down.** Block the cloud metadata address and private network ranges from inside sandboxes. The metadata address is how a sandboxed process gets your cloud credentials. Filter DNS lookups too, because data has left a sandbox through them.

**Environments are separate, and snapshots exist.** An agent deleted a production database during a code freeze in July 2025. Separate environments and snapshots answer that.

**There is a kill switch at the runtime.** It stops a session at once, whatever the model is doing.

**Credentials follow the lifecycle.** Credentials are issued at the entitle stage and removed at retirement, two stages of the [agent lifecycle](/architecture/agent-lifecycle).

The enforcement points here are the sandbox boundary and the egress proxy. Both sit outside the model, so the model cannot argue its way past them. This is [enforcement outside the model](/architecture/enforcement).

## Choices and their verdicts

Each entry is the common choice, tested against the simplest credible alternative. The full records are in the [decision catalog](/decisions).

- [Run your own models or pay per use](/decisions#cd-6): pay per use by default. Run your own only for air-gapped or classified data, rarely for cost alone.
- [Kubernetes everywhere or managed agent runtimes](/decisions#cd-7): split them. Use Kubernetes for model serving if you host models. Use managed runtimes for agent sessions.

## Concerns this layer must honour

A concern is a requirement every layer must honour. This layer carries a specific duty for six of the ten.

- **Identity and access.** It issues one identity per agent. No agent uses a person's login.
- **Sovereignty and residency.** Data sensitivity decides the serving location. Session and sandbox data stay in the region.
- **Privacy.** Session memory is wiped when the session ends. Session logs are redacted.
- **Safety and oversight.** Environments are separate by hard policy. The runtime holds a kill switch.
- **Cost.** It measures cost per session, idle time and hardware use, and enforces budget caps.
- **Resilience.** This layer owns it. Sessions resume after a crash, snapshots restore, and work falls back to human queues.

The full grid of concerns against layers is the [concern matrix](/architecture/concern-matrix).

## Evidence and limits

The isolation, billing, start-time and sovereign-serving claims come from vendor documents. They are marked [vendor]. The strongest independent sources are NIST, the UK AI Security Institute, OWASP, the CNCF and the IETF. Epoch AI, SemiAnalysis and the SANDBOXESCAPEBENCH paper add more.

No confirmed escape from a production microVM, gVisor or Hyper-V agent sandbox had been found as of October 2026. That is an absence of evidence, not proof of safety. One reported gVisor flaw appeared on a single aggregator page only. It needs checking against the project's own advisories.

No peer-reviewed study of self-hosted serving costs exists. The crossover figures above are ranges from four practitioner analyses that agree with each other. Utilisation is the assumption that moves them most. This guide recommends treating them as ranges and measuring your own utilisation.
