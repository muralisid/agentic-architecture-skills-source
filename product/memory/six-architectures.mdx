## What should survive from one task to the next?

Keeping every original record preserves detail but still requires a way to find it. Keeping only a summary makes reading easier but can discard the fact a later question needs. Before comparing memory products, decide what your future tasks must be able to recover. The six designs below make different choices about what is retained and when a model does the work.

A memory for an agent can be built in six ways. It can keep the original words. It can keep a summary, or a list of facts a model pulled out. It can keep a web of who relates to what. It can let the agent write its own notes. Or it can bake what was learned into the model itself. Each choice decides what can be found later, and what is thrown away on the way in.



<span id="ma-intro" />

First, the two questions that place any memory system. Then the six classes those questions produce.

Then where the named systems sit, about forty of them. Then the four managed services from the large cloud providers.

Then three product moves in 2026 that all point the same way. Last, the research line that puts memory inside the model, with no product yet.



## Two questions place any system

<span id="ma-axis1" />

The first question is what is persisted. At one end, the original text, unchanged. At the other end, the model's own weights.

In between sit summaries, extracted facts, and graphs of entities and relations. Each step along that line transforms the original more.

Transformation makes the store smaller and cheaper to read. It also throws away whatever the transformer did not think mattered. That loss is silent, and no later search recovers it.



<span id="ma-axis2" />

The second question is when a model runs. Some systems run a model at write time, once per document. They pay once and read cheaply.

Some run a model only at read time. They store cheaply and pay per question.

Some run a model in the background, between tasks. They pay continuously and hope the consolidation is right before anyone asks.

And some produce the memory by training. The model reads it implicitly, in the forward pass. Where the intelligence is spent is where the cost sits.



<span id="ma-tiers" />

This guide already grades memory by how long it is kept. Those are the tiers, M1 to M5. The tier decides the governance: ownership, consent, retention and erasure.

The six classes on this page are different. They describe how a store at any tier is built.

Both are needed. The tier says what duties attach. The class says what can be recalled.



## The six classes

<span id="ma-six" />

Class one keeps the original text with a search index without generative extraction at write time. Class two keeps facts and profiles that a model pulled out of each conversation.

Class three keeps entities and relations as a graph. Each relation can carry the dates it held. Class four keeps summaries at one or more levels of abstraction.

Class five lets the agent itself read and write memory files through tool calls. Class six puts the memory in weights or caches, written by training. We take them one at a time.



<span id="ma-c1" />

Class one stores the original text, unchanged. It is indexed by embeddings, and usually by keywords too. No generative model extracts or summarizes the records at write time; an embedding model may still create the index.

Keeping the original records preserves details for later inspection. Indexing and access control still have costs. Exact names and quotations remain available to lexical search.

The cost comes later. Nothing is consolidated, so the same fact appears every place it was said. Each encoder has an input limit. Verify how the chosen model handles long units and whether ingestion truncates them.



<span id="ma-c2" />

Class two runs a model at write time. The model pulls out atomic facts, notes, or a profile of the person.

The store is small, readable, and easy to update. A profile can be injected whole into the next task.

The loss is silent and permanent. Whatever the extractor did not think mattered is not in the memory. This is the class most commercial memory layers chose in 2025.



<span id="ma-c3" />

Class three also runs a model at write time. It extracts entities, relations and facts, and stores them as nodes and edges. Often each edge carries the dates it was true.

Retrieval can walk the graph. That buys relationship questions, what was true when, and a path that can be explained.

It costs a model call per document. It adds a second database to run. And on plain factual questions, a sparse graph can do worse than simple retrieval.



<span id="ma-c4" />

Class four keeps summaries. Sometimes at several levels, from a paragraph up to the whole corpus. Sometimes as compressed observations that stay in the model's context.

This buys questions about the whole. What are the themes, what changed over the year. A stable summary also caches well, so it is cheap to reuse.

Detail below the summary level is gone. And summaries drift from the source as the source changes.



<span id="ma-c5" />

Class five lets the agent manage its own memory. It reads and writes files or memory blocks through tool calls. A small core stays in its context every turn.

The agent decides what matters. The files can be versioned like code, and a person can read them.

Quality depends on the agent's judgement at write time. And there is no index over the raw history unless one is added. One vendor moved its whole product to this class in 2026.



<span id="ma-c6" />

Class six puts the memory inside the model. In its weights, in its key-value caches, or in a latent pool. It is written by training, or by learning at test time.

There is no retrieval step at all. In principle the effective context could be very long.

It is research. Nothing has shipped as a product memory layer. An enterprise memory cannot do without erasure and audit. Both are unsolved here.



## Where the named systems sit

<span id="ma-placed" />

Here is where the named systems sit, from their own papers and documentation. Class one holds the verbatim system we tested, and the plain retrieval baseline in every paper. Class two holds most commercial memory layers, and the managed cloud services. Class three holds the graph vendors and the graph research systems.

Class four holds the tree and observation systems. Class five holds the operating-system pattern, the file-based products, and the memory tool from one model vendor. Class six holds the research line: test-time memory, trained caches, and latent pools. Eleven systems span two classes. The full list, with dates, is in the tail of this page.



<span id="ma-fallback" />

Eleven systems span two classes. The spanning pattern is the same each time. An extracted or graph store, with the original text kept beside it.

It is the design answer to one finding, made independently more than once. Replacing the original text with extracted artefacts lowers accuracy.

One 2026 study measured verbatim chunks beating extracted facts by 15.9 points. The largest memory benchmark's authors found the same in 2024. Keeping the text and adding derived keys improved recall by 9.4 percent. Replacing it with facts or summaries made answers worse.



## The managed services

<span id="ma-cloud" />

All four large cloud providers now ship a memory service. One model vendor ships a memory tool: the agent writes files into a directory the customer owns. The first cloud service reached general availability in October 2025.

The second reached general availability in December 2025, and started billing in January 2026. The third was still in public preview in June 2026.

All four store extracted facts and preferences. None stores the transcript. Whatever the extractor did not keep is not in the memory. The transcript, if kept at all, lives elsewhere under different retention rules.



## What changed in 2026

<span id="ma-2026" />

Three product moves in 2026 point the same way. One vendor moved its memory to versioned markdown files in February. In March it deprecated its server-side memory tools.

The largest vendor removed graph memory from its open-source release. It is now a platform feature only, with no open replacement. Its new algorithm adds facts and never overwrites them.

A third vendor stopped supporting its community edition. The open graph engine remains; the hosted product carries the claims. All three moves are towards plainer storage and less transformation at write time.



<span id="ma-baseline" />

Two more signals sit beside the product moves. In the largest vendor's own 2025 paper, giving the model the full conversation scores 72.90. The vendor's best memory variant scores 68.44.

In the second vendor's paper, the full-conversation baseline is within 0.4 of the vendor's system.

Both papers argue the trade on latency and token cost instead. That is a legitimate trade, and a different claim. And a 2026 study found that swapping the embedding model alone moved accuracy by 6.2 points. That is more than the gap between several competing systems.



## Memory inside the model

<span id="ma-research" />

Class six is where the long-run bet sits. One research line updates a neural memory at test time. It reports needle-in-haystack recall beyond two million tokens, and 80 percent on a synthetic test at ten million.

Another trains a small cache per corpus offline. It reports 38 times less memory at inference.

A third trains a fixed-length text memory by reinforcement learning. It reads 3.5 million tokens after training on 8 thousand, with under 5 percent loss. Each is a paper with code and no product. None addresses erasure, permissions or audit.



## What to remember

<span id="ma-recap" />

Here is what to remember. Decide the class before the vendor. The class fixes what is lost at write time, and no later search recovers it.

If you choose an extracted or graph store, keep the original text beside it. The vendors that score best now do.

Count the model calls per document at write time and per question at read time. That is the cost model, and it differs tenfold between classes.

Treat memory in the weights as research until a product can delete a fact on request. The next page looks at how these systems are scored.

## Results and supporting detail

### The six classes
| Class | What is stored | When a model runs | What it buys | Where it breaks |
|---|---|---|---|---|
| 1. Verbatim store, non-model index | The original text, unchanged, in a <Term k="vector index">vector index</Term> and usually a keyword index | Never at write; only as the reader | Nothing lost on the way in; the cheapest ingestion there is; exact names and quotations still findable | Nothing is consolidated, so the same fact appears in every place it was said; long units are truncated by the encoder |
| 2. Extracted fact and profile store | Atomic facts, notes or schema-bound profiles that a model pulled out of each conversation | At write, on the hot path or in a buffer | Small, readable, updatable; a profile can be injected whole | Extraction loses what the extractor did not think mattered; the loss is silent and permanent |
| 3. Graph-structured store | Entities, relations and facts as nodes and edges, often with validity windows | At write, for extraction | Relationship traversal; what was true when; explainable paths | Extraction cost per document; sparse graphs on plain factual questions; a second database to run |
| 4. Hierarchical summary store | Summaries at one or more levels of abstraction, or compressed observations kept in context | At write or in a background pass | Corpus-wide questions; a stable prefix that caches well | Detail below the summary level is gone; summaries drift from the source |
| 5. Agent-managed files and blocks | Files or memory blocks the agent itself reads and writes through tool calls, with a small always-present core | At read, by the agent; optionally in a background sleep pass | The agent decides what matters; versionable; inspectable by a person | Quality depends on the agent's judgement at write time; no index over the raw history unless one is added |
| 6. Parametric and latent memory | Weights, key-value caches or latent pools updated by training or test-time learning | During training or test-time updates; read implicitly | No retrieval step at all; potentially very long effective context | Research stage; nothing shipped as a product memory layer; erasure and audit are unsolved |

MemOS (July 2025) is the one system that claims to span classes 2, 3 and 6 under a single abstraction, holding plain text, activation caches and parametric memory together. That claim is the vendor's.

Eleven systems span two classes, and the spanning pattern that matters for a design decision is the same each time: an extracted or graph store with a verbatim fallback beside it. Graphiti keeps the raw episodes under its edges, Memex(RL) keeps a full-fidelity database behind its learned summaries, and two of the newer entrants lock every recalled fact to its source turn. Each is the design answer to the same finding, made independently in at least two 2026 studies and in the LongMemEval paper of 2024: replacing the original text with extracted artefacts lowers question-answering accuracy. On the LoCoMo benchmark one January 2026 study measured verbatim chunks beating model-extracted artefacts by 15.9 points overall on the three reasoning categories, and the LongMemEval authors found in 2024 that replacing sessions with summaries or facts "negatively impacts QA performance due to information loss" while keeping the text and adding derived keys improved recall by 9.4 percent.

### The managed services
**In short:** All four large cloud providers now ship a memory service, and all four store extracted facts and preferences rather than the transcript.

| Provider and service | Status and date | What it stores |
|---|---|---|
| Anthropic memory tool with context editing | Public beta 29 September 2025; no beta header required as of September 2026 | Files the model writes and reads under a memory directory in the customer's own storage; class 5 |
| AWS Bedrock AgentCore Memory | Preview 16 July 2025; generally available 13 October 2025 | Short-term turn events per session; long-term extracted preferences, facts and session summaries; a self-managed extraction strategy since GA; class 2 |
| Microsoft Foundry Agent Service Memory | Public preview February 2026; procedural memory added June 2026; still preview as of 2 June 2026 | User profile memory, chat summary memory, procedural memory; quotas of 100 scopes per store and 10,000 memories per scope; classes 2 and 4 |

OpenAI offers memory inside ChatGPT (February 2024) and a compaction primitive in its API (March 2026) that folds a long context into an encrypted state item. No first-party long-term memory store for API agents was found as of the access date.

The consequence for an enterprise is direct. Each service applies a model at write time and keeps what that model extracted. Whatever it did not extract is gone from the memory, and the raw transcript, if it is kept at all, is kept somewhere else under different retention rules. The [data-to-memory pipeline](/architecture/data-to-memory) rule that every derivative carries the source's permissions and deletion duties applies to the extracted facts and to the transcript separately.
