## A deleted document can leave a readable memory behind

A restricted incident report is summarized for an investigation. Later, access to the original is withdrawn. If the summary and its index entries remain available under different permissions, an agent can still reveal information from the report. Protecting only the original has not protected the information derived from it.

Track which sources produced each retained representation and how access changes, correction, or deletion affect those representations. This is why ownership and lifecycle belong in the memory design from the beginning.

## Start with ownership

Identify who can authorize the use of a source and who maintains its quality. Keep the permitted purpose and retention requirements with the information. A derived vector or summary should not become a route around source access rules.

## Check access during retrieval

Use the current caller and task authority when selecting evidence. Account for stale permissions and changed membership. Do not reveal restricted source details through explanations, search previews, or diagnostic traces.

## Treat new memories as proposals

An agent may suggest retaining an observation. Check its source, purpose, sensitivity, and reliability before allowing it to affect later tasks. Evidence that a task succeeded once does not automatically justify a new organizational rule.

## Follow the derivatives

Track the raw record, extracted fields, indexes, summaries, caches, and relevant evaluation copies. Corrections and removal requests need a defined route through those derivatives. Where retention duties conflict, follow the approved policy rather than letting the model improvise.

## Keep unresolved issues visible

A summary derived from several sources may be hard to separate when one permission changes. Re-derivation or more restrictive access can be necessary. State the limitation and test the actual implementation.
